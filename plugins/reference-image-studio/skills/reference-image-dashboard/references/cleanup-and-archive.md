# 清理与归档

## 识别范围与检查引用

1. 读取项目索引和登记表，将“这几张”“失败结果”“只保留 V3”等转成具体 task/step/output 或图片路径列表。网页勾选是候选选择，只有用户在对话中下达清理指令后才执行。不能从“失败”状态推定对应图片完全无用；失败 step 也可能留下可用输出。
2. 对每个目标运行 `lifecycle.py inspect`，检查项目参考、保留作品、所有任务输入输出、文档路径中的结构化引用。报告具体任务/引用位置，并搜索相关 INDEX、NOTES、PLAN、prompt 中的路径文字；文本提及仅是补充，不能保证发现所有语义或外部引用。
3. 默认排除参考原件、明确保留作品、用户输入原件、prompt、方案和检查记录。脚本保护已登记 reference/retained；输入原件需要 skill 根据来源职责额外识别，不能只依赖脚本。用户未指定对象时不自行清空所有历史结果。确实无法区分所指版本时只询问这个歧义，继续处理已明确的部分。

## 默认执行：原位归档

用户说“清理这些结果”“删掉这些试稿”但未明确要求释放空间或永久删除时，按可恢复归档完成。先说明本次采用原位归档；用户已明确授权的范围不再重复确认。

```text
python3 <dashboard-skill>/scripts/lifecycle.py inspect <workspace> --path tasks/task-01/outputs/v1.png
python3 <dashboard-skill>/scripts/lifecycle.py archive <workspace> --path tasks/task-01/outputs/v1.png --reason "用户要求清理 V1 试稿，默认归档"
python3 <dashboard-skill>/scripts/lifecycle.py restore <workspace> --path tasks/task-01/outputs/v1.png --reason "用户要求恢复 V1"
```

`--path` 可重复，先核对整批清单。归档只写 `.studio/project.json` 的 `archives`，不移动或改写图片字节，不改旧输入顺序、prompt 或输出身份。原有 task/step/output 和 reference/retained 的来源关系仍可解析；被后续任务用作输入的图片继续显示在其任务详情中，原图链接有效。归档记录保存原因、时间、引用检查和操作历史；恢复移回原分类，操作历史保留。

归档图片在普通参考/任务/保留/未登记列表中隐藏，在“已归档”栏显示，仍可放大、对比及查看原任务。任务详情保留完整输入和输出，避免归档掩盖历史。只有归档记录而图片已缺失时仍应报告缺图，不能声称已安全保留。

用户明确将参考或保留作品也纳入归档范围时，先说明会从当前列表隐藏但文件仍可追溯，记录其明确范围后才使用 `--include-protected`。不删除认可记录，不把归档等同取消参考认可；需要更换标准时另按 workspace skill 更新适用范围/替代状态。

## 用户明确要求其他方式时

- **只隐藏**：解释其影响仅是页面可见性，沿用可恢复的归档状态即可；不宣称删除文件。
- **物理移到归档目录**：不是默认方式。保留旧路径、目标路径、SHA-256 和恢复映射，先枚举结构化及文本引用；在本项目内移动后更新登记、所有受影响 task 路径和可确定的文档链接，再 check/build。无法可靠改写的外部引用应说明，必要时原位归档相关文件；不能对不确定的 prompt 内容做全局替换以伪造历史实际输入。
- **移到废纸篓/释放空间**：仅在用户明确要求时使用有可靠恢复入口的环境能力；不能用永久删除命令冒充废纸篓。保留 provenance、prompt、原路径、恢复位置和操作记录。输入/参考/保留作品或外部引用超出授权时先处理这些具体影响。
- **永久删除**：必须有用户明确的永久删除范围，不从泛泛“清理”推定。列出实际将删除的文件和不可恢复影响，按环境权限执行；有后续引用时优先保留被引用文件，或在用户明确接受断链后保留缺图占位与删除原因。不要删除任务记录来隐藏断链。

## 删除无其他引用的归档文件

用户明确说“把归档中没有其他引用的都删除掉”已给出删除方式与条件，执行范围仅为当前已归档图片，不再默认重复归档。先完成以下检查并列出实际清单、数量、空间与不可恢复影响；已明确授权且范围没有扩大时直接执行，不重复索要确认。

1. 对当前 `archives` 中 `archived: true` 且未删除、实际存在的图片执行 `inspect`。文件自身唯一的 task/step/output 登记属于生成履历，不算“其他引用”；其他输出登记、reference、retained、后续输入、文档引用都要检查。保留原始输入、参考、保留作品及其 origin 输出。
2. 登记表不是完整依赖图。搜索项目文档中的完整路径、文件名和版本简称，实际阅读 NOTES、PLAN、prompt 的“前版为底图”“对照图”等语义，包含同一任务内部的迭代链。其他任务的文本引用及无法确定的输入关系先保留；仅列举自身产出的历史文字不阻止删除。检查与非归档输入/参考/保留副本相同的 SHA-256，并保留这些关联源文件。不要仅凭 grep 无命中宣称无引用，也不从“未采用”推断没有作为错误对照传入。
3. 在 `.studio/` 写删除审计 JSON：原路径、task/step/output、SHA-256、字节数、时间、用户请求、结构化与补充引用检查、保留项及理由。删除前再次核对文件边界、归档状态与哈希；仅删除清单图片，不删除 task.json、prompt、方案、检查记录或其他副本。不为满足条件先删除引用。永久删除不可用逻辑 restore 恢复；中途失败时逐项记录实际完成情况，不声称整批成功或伪造回滚。
4. 每个实际删除的 archive 条目写 `deleted: true`、`deleted_at`，保留 `archived: true`，`reason` 说明主动删除与不可恢复影响；`history` 追加 `action: permanent-delete`、时间、原因、SHA-256、bytes 和 audit 路径。原输出路径、ID 与生成历史保持，允许在输出 title/checks 补充删除说明。只有文件实际删除后才标记删除；不能用此字段隐藏意外缺失。
5. build 后“已删除”栏与任务详情显示删除占位和原因；“已归档”只展示仍归档的文件。缺少文件且没有有效删除登记时仍为异常；登记删除但文件仍存在也报警。核对本次删除数量、实际文件状态、其余图片哈希及保留 origin 链，再 check。可清理这些已删除图片的 Dashboard 缩略图缓存，但相同哈希仍被其他图片使用的缓存要保留。

删除状态的最小记录示例（加入原 archive 条目，而非另造任务）：

```json
{
  "path": "tasks/task-01/outputs/v1.png",
  "archived": true,
  "deleted": true,
  "deleted_at": "2026-10-15T07:00:00+00:00",
  "reason": "用户要求删除无其他引用的归档试稿；原图已永久删除，历史记录保留",
  "history": [{
    "action": "permanent-delete",
    "at": "2026-10-15T07:00:00+00:00",
    "reason": "用户明确要求，引用检查无其他依赖",
    "sha256": "<实际文件哈希>",
    "bytes": 12345,
    "audit": ".studio/delete-audit.json"
  }]
}
```

本 helper 只实现原位归档和恢复，不实现物理移动、废纸篓或永久删除，不能将归档成功当作磁盘清理成功。

## 完成与核对

归档/恢复脚本自动 build，之后运行 dashboard.py check，确认图片字节未改、输入和 origin 仍有效，普通列表/归档栏与操作一致。报告处理数量、排除项及引用影响，提供 Dashboard 链接。若登记或构建失败，修复记录并重建，不静默跳过错误；脚本构建失败会恢复操作前的登记表。已有人工写入的旧索引/来源清单保留历史路径，不因原位归档产生路径变化。
