# 02 存储与迁移

§1 存储形态：独立实体还是内嵌文档 · §2 扁平视图：让调用方无需改动 · §3 迁移：请求逐字节不变 · §4 与旧版本共存 · §5 地址：默认 + 覆盖 · §6 备份与同步 · §7 检查清单

## 1. 存储形态：独立实体还是内嵌文档

线路与线路参数有两种存法：

| 形态 | 做法 |
| --- | --- |
| 独立实体 | 线路表（渠道, 协议族 唯一）、线路参数表（模型, 协议族 唯一） |
| 内嵌文档 | 渠道记录上加「主机」与「线路列表」两个字段；模型记录上加「当前线路」与「其余线路参数」两个字段，后者为结构化文档（如 JSON） |

**选内嵌文档的条件**（全部成立时；任一不成立就用独立实体）：
- 线路从不被单独查询或按条件检索，总是随渠道 / 模型整体读入。
- 线路参数按协议族出现（有的字段只在一个族有），拉成列会得到大部分为空的宽表。
- 希望「写一个渠道」「写一个模型」仍是**单条写操作**，这样备份恢复、合并这类批量操作可以原封不动地装进一个事务。

内嵌时的约束由**解析**保证：同一协议族的第二条丢弃，不认识的协议族丢弃。
解析要**逐字段收窄**，不要整体信任：更新版本写的、或被手改过的值，不认识的一律视为「不存在」（= 不发送），而不是带着未知值发出去。

**存储层不必改名。** 界面把「供应商」改叫「渠道」，但存储结构与内部类型名可以保留——引用面太广，改名换不来任何行为。

## 2. 扁平视图：让调用方无需改动

这是整套设计里性价比最高的一招：

- 渠道原有的「地址 / 协议标准 / 鉴权 / 协议族专属设置」字段**永远保存主线路的值**。
- 模型原有的参数字段**永远保存当前线路的值**；其余线路的参数旁挂保存。

收益：
1. **旧版本读同一份数据，看到的和以前一样。**
2. 运行时大量「拿到模型 → 找它的供应商 → 读协议 / 地址 / 平台」的调用方，只需把「按 id 查供应商」换成**「按模型的线路看渠道」**：
   返回一个渠道副本，其扁平字段被替换成该模型当前线路的值。后续读协议、地址、平台、私有能力的逻辑一行不改；协议适配层不改。

**按模型的线路看渠道**（步骤）：
1. 按模型的渠道 id 找到渠道；找不到 → 无结果。
2. 确定协议族：模型选过且渠道仍提供 → 用它；否则 → 主线路。
3. 在渠道线路列表里取该族的线路；取不到 → 无结果。
4. 由线路算出协议标准与完整地址；鉴权与专属设置取线路的；平台按「官方端点 = 厂商」规则重新解析。
5. 返回替换了这些扁平字段的渠道副本。

**两处不同的降级**：
- 展示与估算（列表、容量预估）在模型选的线路不存在时**退回主线路**，只为不让页面出错。
- **真正发请求的连接解析在这种情况下报错**「线路不存在」，与「渠道不存在 / 模型不存在 / 缺凭据」并列、各有文案。
  绝不静默改走主线路：该模型的参数是按原协议族设置的，换族发出就是跨族请求。

**规范化在每次读与每次写都执行**（幂等）：没有线路列表的旧记录现算一条；有的把扁平字段对齐到主线路。这样「扁平字段是主线路的」是事实而非约定。

**调用方替换要全**：凡是结果流向协议问题（协议族、平台、私有能力、实际请求）的「按 id 查供应商」都要换。
漏一处，就是「切了线路但这里仍按主线路算」。建议用源码扫描或静态检查把旧写法挡住。

## 3. 迁移：请求逐字节不变

推荐**读时迁移**：不写一步迁移程序，每次读取时由旧字段推出线路。理由：推导是纯函数、结果稳定；一步迁移只会多一个会中途失败的环节。

**由旧记录推出唯一一条线路**（步骤）：
1. 协议族与是否官方，取自旧的协议标准。
2. 把旧地址切成「主机」与「其余部分」。**按原始字符串切**（scheme://主机[:端口] 与剩余），不要经过 URL 解析库——它会把主机转小写、补尾斜杠，拼回来就差一个字节。
3. 官方端点：不存主机；旧记录若写了地址，原样作为绝对地址覆盖。
4. 旧地址不是 URL（没有 scheme）：整条作为路径保留，什么都不丢。
5. 其余情况：「其余部分」**恰好等于平台对该协议族的默认路径**时不存路径，否则存为覆盖。
6. 鉴权与专属设置原样带过去。

于是「主机 + (路径覆盖 或 平台默认)」恰好还原旧地址。**为每个旧预设写一条「迁移后地址逐字节不变」的测试**——这是整次迁移唯一需要证明的性质。

迁移**不自动合并**（见 04 篇）。
迁移后唯一允许的行为变化是**「不再发送」**（例如非该平台上不再发某家私有字段），不允许新增发送。受影响的模型在界面上**常驻说明**，而不是只写一次迁移日志。

## 4. 与旧版本共存

扁平字段保存当前线路，所以旧版本打开同一份数据能正常工作。但旧版本保存时只写扁平字段、不知道线路列表——新版本下次读到：扁平字段是新的，线路列表是旧的。

**识别旧版本回写**：写入时，在主线路上**记下当时写进扁平地址字段的值**（写入标记）。读取时：
- 有标记：扁平地址 ≠ 标记 → 被别的版本改过 → 主线路按扁平字段重建，其余线路保留。
- 无标记（更早写的数据）：退回比较「按今天的规则拼出的主线路地址」与扁平地址。

**不能只用第二种比较**：平台默认路径一旦随版本更新，它会把「约定变了」误判为「旧版本改过」，把本应跟随约定的空路径冻结成覆盖值。

**已知缺口要写进文档**：旧版本若以「整行替换」方式保存模型，会清空新字段——模型回到主线路、其余线路参数丢失。只在「升级 → 回退 → 再升级」时发生，一般不值得为它加机制。

## 5. 地址：默认 + 覆盖

| 线路的路径 | 含义 |
| --- | --- |
| 缺省 | 平台约定（如中转站 Chat `/v1`、Gemini `/v1beta`、Anthropic 根路径） |
| 相对路径 | 接在渠道主机后 |
| 绝对地址 | 主机与路径一起替换（有的中转把某协议放在独立子域名） |

- **存覆盖值，不存结果。** 「缺省」与「填了一个恰好等于默认的值」语义不同：前者跟随平台约定，后者冻结。「恢复默认」写回缺省；输入值等于默认时也存缺省。
- **路径只到协议尾巴之前。** 各协议适配层自己补尾巴（`/chat/completions`、`/responses`、`/v1/messages`、`/models/{id}:…`），且补尾巴要幂等（用户多填一段 `/v1` 不会拼出 `/v1/v1`）。
- **官方线路地址锁定**，存空，由适配层常量决定；要改地址就选「自定义」平台。
- **「是否官方」按线路自身判断，不按平台推断**：兼容线路指向厂商主机时，按平台判成官方会在保存时丢掉主机、地址损坏。

## 6. 备份与同步

- 配置备份格式版本 +1；渠道带主机与线路列表，模型带当前线路与其余线路参数。
- **导入旧版本备份走与旧存储记录同一个规范化过程**——一份迁移逻辑，不写第二份。
- **旧版本读新备份：靠版本检查整体拒绝**，不做部分导入。版本检查必须从第一版就存在，且是「大于已知版本即拒绝」。
  没有的话，先单独发一个带检查的版本，再改格式。拒绝文案应说「来自更新的版本，请先升级」，而不是「文件无效」。
- 同步服务端若只保存加密后的不透明数据、不解析内容，则服务端无需改动，加密外壳的版本也不动。多设备共用一个备份位时，所有设备须先升级再恢复。
- 平台画像不进备份。

## 7. 检查清单

- [ ] 旧字段保留并永远保存当前 / 主线路的值；新信息旁挂
- [ ] 读与写都经过同一个幂等规范化
- [ ] 所有「按 id 查供应商后问协议问题」的调用方都换成「按模型的线路看渠道」
- [ ] 每个旧预设都有「迁移后地址逐字节不变」的测试
- [ ] 能识别旧版本回写，且不把平台约定变化误判为回写（写入标记）
- [ ] 请求路径上「线路不存在」是显式错误
- [ ] 备份版本 +1；旧备份与旧存储走同一迁移；旧版本拒绝新备份
