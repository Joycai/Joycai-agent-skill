# 01 数据模型：三个实体 + 一张平台画像

§1 为什么一条「供应商」记录撑不住 · §2 实体与身份 · §3 字段归属 · §4 平台画像 · §5 明确不做

## 1. 为什么一条「供应商」记录撑不住

常见的起点：`供应商 { 地址, 协议标准, 鉴权方式, 凭据 }`，模型挂在下面，所有参数都在模型上；「添加供应商」套一个预设模板，**模板填完就消失**——记录里没有任何字段记得它来自哪家平台。

实测里平台、协议、模型三者的关系是这样的：

| 现象 | 实测样本 | 单记录形状的后果 |
| --- | --- | --- |
| 同一模型在同一平台可走多个协议 | 一家云平台同一凭据提供 Chat 兼容、Responses、Anthropic 兼容三个面；一台中转站一个主机三个协议 | 每个协议一条记录：凭据存多份、模型建多次 |
| 同一模型、同一平台，不同协议上能力不同 | 某模型的代码解释器在 Chat 面被拒（400），Responses 面可用；图片搜索只在 Responses 面有 | 能力挂在属于某协议的模型记录上：换协议 = 换记录 = 重填 |
| 同一模型在不同平台走不同协议 | 同一开源模型：厂商直连、云平台上架版、聚合路由版 | 能表达，但无处说明「这是同一个模型」 |
| 同一模型在不同平台能力不同 | 云平台上架版能跑代码解释器，厂商直连没有任何服务端工具 | **表达错误**，见下 |

最后一行是**行为缺陷**：如果按「协议标准」判断能不能发私有能力，所有「OpenAI 兼容」端点都会收到某一家的私有字段——
轻则被静默忽略（用户以为开了联网，其实没有），重则被拒。根因是「兼容协议 ≈ 某一家」的隐含假设；**只在一家上实测过的能力，必然会被这样泛化**。
修法是把「平台」提升为一等概念（§4）。

## 2. 实体与身份

| 实体 | 含义 | 身份 | 归属 |
| --- | --- | --- | --- |
| 平台画像 | 一家平台的实测事实：提供哪些线路、各线路默认路径与鉴权、各线路认哪些私有能力 | 平台 id | **随软件发布的数据**；不进用户配置，不进备份，用户不可编辑 |
| 渠道 | 用户配置的一条接入 | **凭据** | 用户配置；凭据存进密钥存储，以渠道 id 为键 |
| 线路 | 渠道下某一协议族的地址 | 渠道 + 协议族（每族至多一条） | 从属于渠道 |
| 模型 | 渠道下的一个模型 | 稳定 id | 用户配置 |
| 线路参数 | 该模型在某条线路上的参数 | 模型 + 协议族 | 从属于模型 |

**实体字段（与表示形式无关）：**

- **线路**：协议族；是否官方端点（官方端点地址锁定）；路径覆盖（缺省 = 平台约定，相对路径接在渠道主机后，绝对地址连主机一起替换）；鉴权方式（缺省 = 协议默认）；仅某一协议族才有的设置（如安全设置）。
- **渠道**：id；显示名；平台 id（缺省 = 由地址推断）；主机（scheme + 主机 + 端口，填一次）；线路列表（有序，第一条为主线路）。
- **模型**：id；所属渠道；上游模型名；类型；与协议无关的字段（价格、上下文窗口、能力授权…）；当前线路的参数；当前线路（缺省 = 渠道主线路）；其余线路的参数集合。

### 为什么渠道以凭据为身份，而不是平台或主机

- 同一平台两份凭据（中转站按分组发放，分组决定可用模型）→ 两个渠道，它们的模型清单不同。
- 同一份凭据打三个协议 → 一个渠道。
- 主机不能当身份：国内站与国际站是两台主机、两份凭据；一台中转站是一台主机、一份凭据、三个协议。
- 线路不单独带凭据。若真有平台要求每个协议一份凭据，那就是多个渠道——没有样本前不为它加字段。

### 为什么「当前线路」挂在模型上，而不挂在渠道上

同一台中转站上，不同模型该走的协议不同（新一代推理模型走 Responses、Claude 走 Anthropic、Gemini 出图走 Gemini、其余走 Chat）。
渠道只声明**提供**哪些线路；模型**可用的线路 = 渠道提供的 ∩ 该模型启用过的**。默认只启用创建时那一条，其它由用户逐条加——
不自动给每个模型开全部线路：一条没验证过的线路出现在切换器里，就是一个会报错的按钮。

## 3. 字段归属

判据只有一问：**「同一渠道、同一模型，换一个协议，这个值会变吗？」** 会变 → 线路参数；不会 → 模型。
**只下沉有实测证据的字段**——下沉有代价（每条线路各填一次）。

| 字段 | 归属 | 判据 |
| --- | --- | --- |
| 地址 | 渠道主机 + 线路路径 | 主机填一次，路径每条线路可改 |
| 协议标准（协议族 × 官方/兼容） | 线路 | 原有的「协议标准」可保留为**派生值**，协议适配层不必改 |
| 鉴权方式、协议族专属设置 | 线路 | 随协议 |
| 凭据、平台 | 渠道 | 身份 / 画像引用 |
| 上游模型名、显示名、类型、启用 | 模型 | 身份 |
| 价格 | 模型 | 换协议计费不变（无反例） |
| 上下文窗口 | 模型 | 权重决定，与传输格式无关 |
| 能力授权：服务端工具、文档输入、视频输入 | **模型（授权）** + 画像 × 线路决定能否发出 | 「允许这个模型联网」属于模型；「这条线路上能不能说出来」属于画像 |
| 思考：类目 / 强度 / 预算 / 方言 | **线路参数** | 同一模型在三个协议上三种说法，类目本身按协议族定义 |
| 最大输出（含实测值） | **线路参数** | 有的协议每次必发、有的只作规划；有的平台把思考计入其中 |
| 温度 | **线路参数** | 是否支持取决于协议族；有的协议开思考时强制固定值 |
| 结构化输出模式 | **线路参数** | 各协议支持的形状不同；学习到的「能力上限」本来就按协议记 |
| 仅一个协议族才有的输出选项 | **线路参数** | 只在那个族有意义 |
| 实测时间与实测值 | **线路参数** | 一次测量测的是一条线路 |

**该拆的信号**：代码里已经有「按协议族丢弃不匹配的字段」「以 (协议, 地址, 模型) 为键缓存学到的能力」这类逻辑——说明系统早就按线路粒度在思考，只是存储没有。

## 4. 平台画像

把一次性的预设模板升级为**被渠道引用的只读数据**。每个画像包含：

| 字段 | 说明 |
| --- | --- |
| id、显示名 | — |
| 官方主机 | 中转站 / 自建 / 本机服务缺省，由用户填 |
| 主机匹配表 | 用于从地址推断平台 |
| 线路表 | 每个协议族：默认路径、是否官方、默认鉴权 |
| 私有能力表 | 每个协议族上有哪些私有能力；可带「按模型名的闸门」，返回 是 / 否 / 未实测 |
| 起步模型 | 新建渠道时预置 |
| 出处 | 每条事实指回一次实测（哪份记录、哪天） |

三条规则：
1. **私有字段的拼写按 (平台, 协议族) 分派，不按协议标准。** 「自定义」与中转类平台的兼容面上**没有任何私有扩展**。
   协议**原生**的工具（某些协议规范内的联网搜索）在中转平台上标「取决于上游 · 未实测」，允许用户自担风险开启；本机服务显式声明没有，不继承「未实测」。
2. **「自定义」是合法平台，不是错误状态。** 推断不出、自建网关都归入这里：只有协议标准部分。
3. **画像随软件发布，不进配置、不进备份、不可编辑。** 渠道只存平台 id；画像更新时所有渠道自动获得新知识，无需迁移。
   旧版本读到不认识的平台 id → 按「自定义」处理。用户要表达「这台中转也认 X」，用「自定义 + 未实测开关」，而不是改画像。

**平台 id 的存法**：只在用户选择的平台**与地址推断结果不同**时才存（中转站、代理域名）；相同则不存。否则一次保存就把当时的推断冻结，以后画像新增的主机匹配永远到不了这条记录。
**官方端点永远按厂商算平台**，覆盖存储值：一条记录改成官方端点后，存着的旧平台 id 不能把私有字段带到官方地址。

## 5. 明确不做（没有样本就不加）

- 线路级凭据；同一协议族多条线路（同族两个区域 = 两个渠道）。
- 按单次请求临时切线路：线路是模型的配置，不是请求参数；需要时建第二个模型。
- 画像进备份或可由用户编辑。
- 出图、转写等**专用接口**的线路参数：它们选的是专用端点（图片生成接口、原生异步任务、本机工作流服务），不是对话协议——
  不显示协议徽标，永远不出现在对话模型的线路切换器里，参数仍存在模型上。
