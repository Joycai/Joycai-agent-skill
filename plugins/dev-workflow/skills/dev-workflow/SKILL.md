# 开发工作流

把一个需求或 bug 从接收做到开 PR。流程分 8 个阶段，每个阶段的产出都落盘成文件，阶段之间靠文件交接，不靠对话记忆。

## 总原则

1. **产物落盘。** 所有阶段文档放在 `.claude/tasks/<slug>/` 下（slug 取自任务名，小写短横线，如 `add-export-button`、`fix-login-timeout`）。目录结构：
   - `00-task.md` 原始需求、任务类型、验收标准
   - `01-scope.md` 代码范围定位结果
   - `02-design.md` 设计文档
   - `03-ui-spec.md` UI 设计说明（仅涉及 UI 时）
   - `04-plan.md` 执行计划，同时是进度表
   - `review/commit-<n>.md` 每片提交的 review
   - `review/final-<n>.md` 整体 review 每一轮
   
   默认不把这个目录提交进仓库（确认 `.gitignore` 里有 `.claude/tasks/`，没有就加上）。项目若要求归档设计文档，把 `02-design.md` 复制到项目的文档目录再提交。
2. **子代理从空白上下文开始。** 派出时任务说明必须自包含：目标、要读的文件路径、范围限制、输出文件路径和格式、返回消息的要求。完整内容写文件，返回消息控制在 10 行以内。定位和 review 类子代理不修改源码。
3. **三个确认门。** 设计文档、UI 设计稿、执行计划各需要用户确认后才进入下一阶段。执行阶段不再打断用户，除非必须偏离计划。
4. **阶段边界可以压缩。** 每个确认门通过后，提示用户此时可以 `/compact`，因为产物已经在磁盘上。会话重启或 `/clear` 之后，先读 `.claude/tasks/<slug>/` 下的文件恢复进度，`04-plan.md` 里的完成标记就是断点。
5. **分支。** 开始前确认工作树干净（不干净先问用户怎么处理），从主分支切出 `feature/<slug>` 或 `fix/<slug>`。
6. **指定模型。** 派子代理时按下文要求指定 model。如果当前环境派出时不能指定模型，则在 `.claude/agents/` 下定义对应代理并在 frontmatter 里设 model。
7. **补丁反复堆叠就转为局部重构。** 同一块逻辑上反复出现大量添加和修补，说明它的结构已经装不下现在的需求，再补只会换个角度继续出问题。这时停下来，把这块逻辑按「已有逻辑 + 新需求」重新设计，而不是再加一层。信号和做法见文末「补丁堆叠：转为局部重构」，各阶段在哪里检查见对应阶段。

## 阶段 0：接收任务

1. 判断任务类型：需求实现还是 bug 修复。
2. 从用户输入提炼一句话目标和验收标准草稿。有不清楚的地方一次问完，不要分多轮问。
3. 建目录，写 `00-task.md`：原始需求原文、类型、目标、验收标准、用户给的约束。
4. 查修补历史：对任务涉及的模块跑 `git log --oneline -- <文件>`，看最近的提交和 PR 里是否已经在同一块逻辑上反复修补；本任务的范围是否来自上一个任务留下的「剩余已知问题」。是的话在 `00-task.md` 里注明，阶段 2 必须先判断要不要局部重构。
5. 判断是否走快速通道（见「快速通道」一节）。命中补丁堆叠信号的任务不走快速通道。

## 阶段 1：定位范围（子代理，sonnet）

派一个只读子代理（工具限 Read、Grep、Glob，可以写 `01-scope.md`），model 用 sonnet。任务说明包含 `00-task.md` 的路径和以下要求：

- 找出与任务相关的文件，每个写路径和一句话作用。
- 画出相关的调用链或数据流：入口在哪、经过哪些模块、落到哪里。
- 列出已有的相关测试和可复用的组件、工具函数、设计 token。
- 列出项目约定：框架、目录规范、状态管理方式、错误处理方式。
- bug 修复时额外给出：可疑位置及理由、复现路径、日志或错误信息出现的位置。
- 对要改的模块，写出它现在负责什么：状态归谁、有哪些写入方、边界在哪；并标出文末「补丁堆叠」信号里已经出现的那些（例如同一个包装已在多个调用点重复出现）。
- 只报告确认相关的内容；不确定的标“可能相关”。
- 写入 `01-scope.md`，返回消息只包含文件路径、相关文件数量、5 行以内的摘要。

主代理收到后读 `01-scope.md`，抽查两三个关键文件核对，不要通读全部。

## 阶段 2：设计文档（主代理）

写 `02-design.md`，内容：

- 目标与非目标（明确这次不做什么）。
- bug 修复：根因分析，说明为什么会出错、为什么现有代码没拦住。
- 方案：改动哪些模块，数据模型、接口、状态的变化，新增或修改的函数签名。
- 形状判断（改动已有代码时必写）：把「这个模块现在负责什么」和「新需求要它负责什么」并排写出来，明确回答现有结构还合不合适。命中补丁堆叠信号的，备选方案里必须有一个局部重构方案，并写清它和打补丁各自的代价；默认倾向重构，选补丁要写理由。
- 备选方案与取舍理由（至少考虑过一种别的做法）。
- 影响面与兼容性：哪些调用方受影响，是否需要迁移或兼容旧数据。
- 测试策略：单元测试、集成测试各覆盖什么。
- 风险与未决问题。
- 是否涉及 UI/UX：新增或修改页面、组件、交互、文案的算涉及；纯逻辑或样式微调不算。

**确认门：** 把设计文档的要点摘要给用户，等用户确认或修改。用户修改的，更新文件后再进下一阶段。

## 阶段 3：UI 设计（仅涉及 UI 时；子代理，主模型或 opus）

先确认子代理能访问项目绑定的 Claude Design：派出前检查该工具是否对子代理可用。不可用则由主代理自己做这一阶段，流程相同。

派子代理，model 用 opus 或当前主模型。任务说明包含 `02-design.md`、`01-scope.md` 的路径，以及：

- 用项目绑定的 Claude Design 出设计稿，遵循 `01-scope.md` 里列出的现有组件和设计 token，不要另起一套风格。
- 写 `03-ui-spec.md`：页面和组件清单；每个组件的加载、空、错误、正常四种状态；布局、尺寸、间距、颜色（用 token 名）；交互和动效；响应式断点；与逻辑层的接口，即需要什么数据、触发什么事件。
- 返回消息：设计稿的链接或位置、`03-ui-spec.md` 路径、5 行以内的摘要。

**确认门：** 用户看稿。有修改意见的，把意见原文写进任务说明再派一次子代理，直到用户认可。

## 阶段 4：执行计划（主代理）

写 `04-plan.md`。先列分片，每片包含：

- 目标（一句话）。
- 涉及文件（新增、修改分开列）。
- 具体改动。
- 要写或要改的测试。
- 验收标准。
- 依赖的前置分片。
- 预定的 commit message。
- 状态：待做 / 进行中 / 已提交 / 已 review。

分片原则：每片完成后能独立编译并通过测试；单片改动控制在一次能 review 完的大小；按依赖顺序排，通常先逻辑层再 UI 层；简单任务只分一片。

**确认门：** 把分片列表给用户确认。

## 阶段 5：分片实现与提交

对每一片按顺序做：

1. 把状态改成“进行中”，只做本片计划内的内容。
2. **偏离处理。** 发现计划有问题时先停下，在 `04-plan.md` 里记录偏离内容和原因。不改接口、不增减分片的小偏离，记录后直接继续；其他偏离先告知用户，等确认。不要静默偏离。实现中发现自己在补丁堆叠（信号见文末），不算小偏离：停下，告知用户，回到阶段 2 改设计。
3. 跑项目的测试、lint、类型检查，全部通过后再提交。
4. 只 `git add` 计划内的文件，不用 `git add -A`。commit message 用计划里预定的，遵循项目的 commit 规范。一片一个 commit。
5. 状态改成“已提交”，进入阶段 6。

## 阶段 6：单片 review（子代理）

每次提交后派一个新的 review 子代理。模型按复杂度选：改动在 200 行以内、不涉及并发、安全、数据迁移、核心业务逻辑，用 sonnet；否则用 opus。

任务说明包含：本片的 commit 范围、`04-plan.md` 里本片的目标和验收标准、`02-design.md` 路径，以及要求：

- 判断改动是否真的完成了本片目标，是否与设计文档一致。
- 找是否引入新 bug 或回归，是否有调用方没同步修改。
- 检查测试是否覆盖了验收标准。
- 检查是否有超出本片范围的改动。
- 必须读 diff 周围的代码和调用方，不能只看 diff。能跑测试就跑。
- 只报告能说清触发条件的问题，不确定的标“待确认”，不报风格问题。
- 写入 `review/commit-<n>.md`，每条含位置、严重程度、确定性、问题、建议修法。返回消息只包含问题数量和最严重的三条。

主代理甄别：逐条判断是否成立。不成立的在 review 文件里写明理由，不要静默忽略。成立的修复，跑测试，作为本片的后续 commit 提交（message 注明是 review 修复）。然后状态改成“已 review”。

修 review 问题前先写一句：这个修法对其他调用方、对称的情况有什么影响；说不清就先不改。如果修法是在共享逻辑上再加一个特例，或者这已经是同一块逻辑上第二次为新的边界情况打补丁，不要修，按补丁堆叠处理（见文末）。

## 阶段 7：整体 review 循环

所有分片完成后，对整个分支的 diff（相对主分支）做整体 review。每轮：

1. 派新的 review 子代理，model 用 opus。任务说明除了阶段 6 的要求，再加上：分片之间是否一致；`02-design.md` 里的每项是否都落实；`00-task.md` 的验收标准逐条核对；有没有死代码、残留的调试输出、未更新的文档和配置。把上一轮的 `review/final-<n-1>.md` 也给它，让它标出哪些已修复，避免重复报告。写入 `review/final-<n>.md`。
2. 主代理甄别、修复、提交、跑全量测试。
3. 判断是否进入下一轮。

**终止条件**，满足任一即停：

- 本轮没有“确认”级别的成立问题。这是正常结束。
- 已经做完 3 轮。
- 本轮报出的问题与上一轮相同，或某个问题修了又出现。这说明修法有分歧，继续循环没有意义。
- 连续两轮在同一块逻辑上报出新的边界问题，或者上一轮的修复引入了回归。这说明是在补丁堆叠，review 循环测出来的只是补丁的覆盖面，不会收敛。

因为后三条停下时：不再自行修改，把剩余问题和停止原因列给用户，由用户决定是继续、放到 PR 里说明，还是另开任务。因为最后一条停下时，同时给出局部重构的提议（见文末）。

## 阶段 8：开 PR

1. push 分支。
2. 用 `gh`（或项目惯用的工具）开 PR。项目有 PR 模板或 CLAUDE.md 里有 PR 规范的，以其为准。
3. PR 描述包含：背景与目标（来自 `02-design.md`）、改动列表（按分片）、测试情况、review 轮次、剩余已知问题、UI 设计稿链接（如有）。
4. 有未解决问题的开成 draft 并在描述里注明；没有的开成 ready。
5. 把 PR 链接给用户，附一句剩余问题的说明。剩余已知问题只是记录，不自动成为下一个任务的范围；窄窗口、低严重度的由用户决定修不修。同一模块上剩余问题还在不断冒出时，建议的下一步是局部重构，而不是再修一轮。

## 快速通道

任务满足以下全部条件时走快速通道：涉及文件不超过 2 个、改法明显、不涉及 UI、不涉及数据结构或接口变化。例如 typo、单行逻辑修正、配置调整。

快速通道跳过阶段 1 和 3，阶段 2 和 4 合并成一份简短的 `02-design.md`（根因或改法、涉及文件、验收标准）。仍然要做一次 review（阶段 6）和开 PR。判断为快速通道时先告诉用户，用户不反对再执行。

## 补丁堆叠：转为局部重构

**信号。** 在同一块逻辑上出现下面任意一条，就说明它的结构已经装不下现在的需求：

- 同一个包装、守卫或检查，要在多个调用点重复加，漏一处就出错。
- 同一份状态要在两处之间来回同步（例如一份在 store、一份在组件里）。
- 一个启发式要靠调用方递提示，或者要加特例来区分是谁在调用。
- 修复是在共享逻辑上加特例条件，修好了这一种情况，弄坏了对称的另一种。
- 连续两轮 review 在这块逻辑上报出新的边界问题，或修复引入了回归。
- 最近几个任务都在修这块逻辑，而且每个任务的范围都来自上一个任务留下的剩余问题。

**做法。**

1. 停下，不再往上加。已经做了一半的补丁不必撤，但不再继续。
2. 把这块逻辑的形状重新推一遍：它现在负责什么，新需求要它负责什么；状态归谁、写入从哪里进、边界在哪。目标是让状态只有一个拥有者、写入只有一个入口，让刚才那些特例不再需要存在。
3. 范围是局部的：只动装不下需求的那个模块和它的直接调用方，不借机大改。
4. 写成设计（更新 `02-design.md` 或另开任务），写清重构方案、打补丁方案各自的代价，以及这块逻辑之前修补过的记录。交给用户确认，这仍然是确认门，任何「不要停」的指令都不跳过它。
5. 用户确认后按正常流程分片实现。给不变量补上性质测试（随机操作序列 + 断言），测试直接调用真实产生改动的函数，不手写「以为它会产生的结果」。
