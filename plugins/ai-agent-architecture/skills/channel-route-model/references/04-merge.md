# 04 合并：同一凭据的多个旧供应商

§1 只检测、由用户确认 · §2 候选条件 · §3 合并计划 · §4 执行顺序与引用改写 · §5 应当被测试钉住的性质

## 1. 只检测、由用户确认

迁移后，原先按协议拆开的多条记录（「X 平台」「X 平台 (Claude 格式)」）仍是多个渠道，各一条线路。
合并要判断两份凭据是否同一份、两边同名模型是否同一个——**判断错了，一个模型就会悄悄换到另一个计费账户**。
所以迁移只做不可能出错的事；合并只**检测**并提示，由用户预览后确认。

合并是整个系统里**唯一让模型 id 消失**的操作，应按「删除」的标准设计与测试。

## 2. 候选条件（全部满足）

- 平台相同；主机相同（规范化后比较：去尾斜杠、忽略大小写）。
- **凭据相同**：只在内存中比较，永不显示、永不写日志。
- 协议族**不相交**（同族两条线路 = 两个渠道）。
- 空凭据只与**同一真实主机**上的空凭据配对（同一地址的两个本机服务就是同一个）；没有主机的不配对。
- 每个渠道至多出现在一个候选对里，避免提供两个争夺同一记录的合并；靠前的一方保留。

**读凭据是有代价的**：系统密钥存储在某些平台上每次读取都可能弹出授权对话框。只读取「平台与主机都与其他渠道相同」的那几份，打开设置页不应连续弹框。

## 3. 合并计划（纯计算，不触碰存储）

输入：保留渠道 K、被并渠道 A、全部模型。输出：新渠道、要写入的模型、要删除的模型、id 映射（旧 → 新）、计数。

1. **新渠道** = K，线路列表 = K 的线路在前（主线路不变）+ A 的线路追加，经规范化。
2. 对 A 下的每个模型 m：
   1. 记下 m 当前的协议族 f（按 A 解析）。
   2. 在 K 下找「上游模型名与类型都相同、且尚未被别的模型并入」的模型 k（一对一：同名的第二条不覆盖第一条）。
   3. **找到 k**：m 的当前线路参数成为 k 在 f 上的线路参数（k 自己已有的线路参数优先保留）；m 进入删除列表；映射 m → k。**保留 k 的 id 与它自己的字段。**
   4. **找不到**：m 搬到 K 下，并把「当前线路」**显式写为 f**——K 的主线路可能与 f 不同，m 不能跟着变。
3. 预览逐条列出：线路并入情况；合并几个、搬迁几个；将被改写的引用数量。

## 4. 执行顺序与引用改写

**一个事务内**，按顺序：
1. 写新渠道——线路要先存在，模型才能指向它。
2. 写所有更新 / 搬迁的模型——搬迁的模型先改归属，才不会被随后的级联删除带走。
3. 删除被并入的模型。
4. 删除 A 下剩余的模型。
5. 删除渠道 A。

**事务提交之后**，按顺序：
1. 应用状态里所有指向被删 id 的选择（默认模型、各功能的专用模型、各辅助代理的模型绑定）按映射改写并持久化。
2. 当前可访问的用量记录按映射改写。够不到的（例如其他项目的独立数据库）会显示为「已删除的模型」——与直接删除该模型的结果一致；写进文档，不必为它做跨库扫描。
3. **最后**从密钥存储删除 A 的凭据。顺序与「重置应用」相反：重置时要先删密钥（配置记录是唯一的凭据清单），合并时要等配置确认不再引用它。

## 5. 应当被测试钉住的性质

- 凭据不同永不配对；协议族相交永不配对
- 同名模型合一、保留方 id 不变、被并方参数成为线路参数
- 搬迁的模型经「按模型的线路看渠道」得到的仍是原协议与原地址
- 写入顺序：渠道 → 模型 → 删除；只有一个事务
- 状态、辅助代理绑定、用量全部改写；删除凭据发生在事务与用量改写之后（断言调用顺序）
