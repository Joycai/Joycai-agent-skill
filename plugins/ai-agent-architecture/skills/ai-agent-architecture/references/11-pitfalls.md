## A. 协议层 · 静默失败类

1. **Anthropic 不回传 thinking block → 思考静默消失。**
   现象：无任何报错，模型只是不再思考（唯一判据：响应里还有没有 thinking block）。
   原因：Anthropic 对不合法思考历史的反应是静默剥离而非 400（DeepSeek 相反：不回传就 400）。
   对策：工具轮 assistant 消息原样带回全部 thinking/redacted_thinking 块（含 signature，
   顺序不动）；`redacted_thinking` 只有不透明 data 也要回。

2. **Gemini 中继发 snake_case 图片字段 → 图片静默不可见。**
   原因：proto3 JSON 让官方 `inline_data`/`inlineData` 两种都收，中继只收文档写的那种，
   未识别键被忽略而非拒绝。
   对策（可移植规则）：面向兼容层时，在「官方两种都收」的地方**选中继文档写的那一种**。
   【2026-09-26 补】Vertex 后端（3.8 Flash，经 OrcaRouter）`inlineData` / `inline_data` 都看得见图——「官方两种都收」再次确认（02 §2.2）。

3. **换模型不剥 thinking block → 静默计费。**
   别的模型不拒绝、静默忽略、照 input 计费。对策：回传载体带 `modelId`，不匹配整组丢弃。

4. **`display` 默认 omitted → 付了全额思考费拿不到一个字。**
   当前代 Claude 的 thinking 默认 `"omitted"`（省延迟不省钱）。对策：恒发
   `display:"summarized"`（schema 里没这个字段的方言除外——文档没写的不发）。
   【2026-09-26 补】Sonnet 5 / Opus 5.5 **连 `thinking` 都不发也在思考**（adaptive 是默认，`display` 默认 omitted）：「跟随默认」档同样付思考费、看不到字（03 §3）。

5. **静默截断 prompt（ollama 等本地栈）。**
   现象：200 + 看似正常的回复，system 指令悄悄没了。原因：超窗从头部丢弃。
   对策：发送前 `ContextSizeError` 估算拦截 + 探测 truncation check + 读实际生效的 `num_ctx`。

6. **HTTP 200 + 体内错误的两种拼法。**
   SSE 体内 `data:{"error":...}`；MiniMax `base_resp.status_code`。只认一种会把过期密钥
   读成正常空回复。对策：两条错误通道都解析；**「200 且没有任何内容」当可疑而非成功**。

7. **内容拦截在半截文本后到达。**
   Gemini blocked finishReason / Anthropic `refusal` / OpenAI `content_filter` 都可能在
   文本已开始流出后到。对策：一律 throw 而非当正常结束——已交付的文本需要作废。

8. **`stream_options.include_usage` 是兼容层最先没实现的东西。**
   现象：usage 全 0 不报错。对策：照发，但把 0 当「没报」处理；探测标 `no-usage-reported`。

9. **同一端点、两代模型，思考控制字段与默认值都不同（千问 DashScope）。**
   现象：默认关思考的商业款（qwen3-max 一类）永远不思考，无任何报错；或强度设置
   在老款上静默无效。原因：老款/商业款的开关是顶层 `enable_thinking`，新款（3.7+）
   接受标准 `reasoning_effort`，默认值也按代分裂（3.5+ 默认开、商业款默认关）。
   对策：作者声明 `switch` 方言（① 族拼法 `enable_thinking`），字段互斥、默认路径与
   `stream: true` 限制见 03 §3 `switch`。

10. **① 族兼容层的服务端搜索无痕——不生效完全无症状（千问 enable_search）。**
   现象：`enable_search: true` 发了，但无法从响应判断搜没搜——千问文档明载
   Chat Completions 模式**不返回搜索来源、不支持角标**，答案直接吸收检索结果。
   于是「字段没生效」和「搜了但没痕迹」在客户端完全同相。
   对策：执行日志对这条线诚实地**什么都不显示**（不要伪造事件）；验证只能靠
   时效性问题对比开关前后的答案；把「生效与否」列入实测清单而不是当作既成事实。

## B. 协议层 · 会响但难排查类

11. **MiniMax Anthropic 端点：turn 停在搜索结果上报 `end_turn`，且拒收自己发的块。**
   兼容层「响应侧抄全了、请求侧没抄」的典型。对策：以「结果之后模型说话了吗」为续跑
   判据；续跑退化为纯文本 transcript（见 05 篇）。

12. **tool_calls 流式拼接键用 id → 交错调用拼错。**
    id 自身也可能分片。对策：按 `index` 分组，id 累积拼接。

13. **强制 tool_choice 撞上思考模型/被砍档端点。**
    对策：结构化输出必有「强制失败→JSON mode」降级链，降级路径仍带原生 JSON 参数；
    回退判定正则要求「能力词 + not supported」**同现**——裸子串会把无关上游错误
    （"does not support streaming for this region"）也吞进回退，翻倍花钱且掩盖真错。
    砍档有动态变体（千问思考开启时 `tool_choice` 只剩 `auto|none`），降级条件见 04 §4。

14. **`json_object` 的 "json" 字面量前置条件。**
    prompt 里没有 "JSON" 字样会报错或产生无限空白流。对策：检测 prompt，缺则追加 cue；
    prompt 可编辑的系统不能把它当既成事实。

15. **兼容层把思维链塞进正文 `<think>…</think>`，标签跨 chunk 分片。**
    对策：状态机切分器——只认响应开头、`danglingPrefix` 扣住可能成为标签的尾巴、
    流结束未闭合按 reasoning flush；切出的思考只展示不回传。

16. **Anthropic base URL 约定与 OpenAI 生态相反。**
    OpenAI/Gemini 的 base 自带版本段，Anthropic 的 base 是根地址（客户端补 `/v1/messages`）。
    对策：不对称归一化；绝不给 OpenAI base「修复性」补 `/v1`（中继合法路由在 /v1 之下）。

17. **鉴权头两套一等约定（Anthropic 生态）。**
    `x-api-key` 与 `Authorization: Bearer` 各有网关只认一种。对策：compat 端点提供
    default/bearer/both 三模式；官方端点只给 default（api.anthropic.com 拒绝双凭证）。

18. **usage 口径：Anthropic 三桶要相加、Gemini 思考在 candidatesTokenCount 之外。**
    直接读 `input_tokens` 会少报一个数量级；只读 candidates 会漏掉最贵的思考。
    对策：归一化为 input/output/cached（cached 是 input 子集）三字段再入库。

## E. 文档与调研方法

54. **指南页 ≠ 参考页。** 判断能力边界看 API 参考页；大文档抓原文自己搜（网页摘要工具
    连续漏掉 295KB 参考页里的关键定义，curl+grep 一次找到）。
55. **兼容层文档四条规律**：结构照抄；扩展在响应侧；枚举是子集；最需要确认的部分
    （流式格式、错误通道、回传规则）不写且滞后上游一年。推论：兼容层文档不能当能力
    清单——「没列」按「未知、需实测」处理。

## F. 图像生成（详见 13 篇）

56. **短时效签名 URL 直接入库 → 图库静默腐烂。**
    现象：生成当时一切正常，几小时后图全部 404（DashScope 明文 24 小时过期，
    多数中继更短）。对策：拿到 URL 当场下载内联成字节；已计费的图值得一次重试；
    下载校验 content-type（200 + HTML 错误页会写出打不开的 `.png` 而 UI 报成功）。
57. **「Unsupported parameter …」prose 命中降级正则 → 二次计费重生成。**
    编辑降级（重试为纯生成）是另一次全价调用，宽松方向的误判直接翻倍账单。
    对策：结构化 code/param 优先——`param` 存在即「请求被理解了」，不是路由缺失；
    只有指名模型的（`param:"model"`、model_not_found 类 code）才降级；模型自己
    回的文字（NoImageError）永远不算证据。
58. **DashScope 错误在顶层 `{code,message}` 而非 `{error:{…}}` → 结构化信息丢失。**
    后果：`DataInspectionFailed`（内容审核拒绝）丢掉 code 后掉进 prose 正则，
    可能被误读成「端点不能编辑」。对策：错误 body 解析兼容两种形状；任务失败时
    code/message 嵌在 `output` 里，抛错时把 `output` 整段作为错误 body。
59. **尺寸分隔符方言：DashScope 写 `宽*高`，通用代码 `split("x")` 静默解析失败。**
    现象：按宽高比挑尺寸永远落回 sizes[0]，无任何报错。对策：解析分隔符放宽
    `/[x*×]/`；发出前按端点拼写归一（`1024x1024` → `1024*1024`）。
60. **异步出图任务挂死后无从排查；「停止」按钮要等下一次轮询才生效。**
    对策：task_id 提交成功后立刻写 API 日志（mid-call note，等成功日志就永远
    拿不到了）；一个总 deadline 罩住提交+轮询+下载全程，与用户 signal 合成后
    喂给每次 fetch **和轮询间的 sleep**——sleep 本身可被 abort 打断。

## G. ② Responses 族与中转站（详见 02 §7、06 §4）

61. **中转站静默改写 effort / temperature。**
    现象：200、输出正常，但发 `max` 回显 `none` 且 0 推理 token；发 `none` 回显 `medium`；
    `temperature:0.5` 回显 `1.0`。原因：中转站/档位/后端替你改了参数，客户端分不清是谁。
    对策：终止响应回显比对，不一致记 `wireRewrites` 进 API 日志与执行日志；只报告不重试；回显缺失不报。
    **（2026-09-24 复测，另一台：「`max` 回显 `none`」未复现，`none` → `medium` 与 `temperature` → `1.0` 复现；改写随时间与上游出没，比对要常开，见坑 161、162。）**
62. **不发 system 就被注入几千 token 的系统提示。**
    现象：输入 token 莫名 4.4K–9K，输出不受影响。原因：New API 中转站在 `instructions`（Chat 面是 system 消息）
    缺失时注入 Codex 系统提示。对策：永远显式发 system；② 族 `instructions` 恒发，哪怕空串。
    **（2026-09-24 补充：① 面带 system 也挡不住——账号池两档带 system 仍注入 4.4K，只有 ② 带 `instructions` 稳定不注入；
    而网关上游反过来见 `instructions` 就挂护栏，「恒发」要改成按上游裁决，见坑 159、165、169。）**
63. **`text.format` 显式 `strict:true` → 中转站整个丢掉 format。**
    现象：回显 `{type:"text"}`，输出不按 schema，无报错。对策：json_schema 不发 `strict` 键
    （官方省略即自动 strict），schema 仍 strictify。
    **（2026-09-24 被扩展：另一台的 `[Pro]` 档不论写不写 `strict` 都丢，① `response_format` 也丢；省略 `strict` 仍对，但救不了这种上游，见坑 160。）**
64. **② 族工具定义省略 `strict` → 端点自动 strict，非 strict schema 被改写契约。**
    现象：带可选字段/未声明 `additionalProperties` 的工具开始 400 或参数被强制全填。
    对策：工具定义显式 `strict:false`（与 63 方向相反，同一个自动 strict 事实）。
65. **`max_output_tokens` 被无视 → 截断永远不会报。**
    现象：设了上限照样写完、`status: completed`，`incomplete` 从不出现。对策：不依赖端点执行输出上限；
    截断相关逻辑（如 JSON 解析失败的归因）不能假设"没报截断 = 没超长"。
    **（2026-09-24：同台 GPT 三个账号档都无视（① `max_completion_tokens` 同），网关上游执行；回显比对抓不到这一条，06 §4.1。）**
66. **Grok 4.5 / 4.6 拒 effort `none`——「关闭」芯片必 400。**
    原因：这两款关不掉思考；全系还拒 `max`。对策：菜单不按型号裁剪、让端点 400 说话，但 UI 提示写明；
    实测套件按型号选"最便宜可接受的档位"，别让一个已知 400 拖红无关用例。
67. **xAI 拒总像素 < 512 的图片（测试夹具太小）。**
    现象：16×16 夹具 400 `below the minimum of 512 pixels`，看起来像图片输入不支持。对策：夹具至少 32×32。
68. **原生 tool search 的回传条目没带回 → 加载过的工具下一轮静默消失。**
    原因：OpenAI 要求下一轮 `input` 带 `tool_search_output`（及 `additional_tools`），只回传
    reasoning / function_call / message 的实现会丢掉它们，且回传缺失无报错。对策：采用原生机制前先扩充回传名单。
69. **Gemini 请求带 `defer_loading` 字段 → 整个请求被拒。**
    原因：③ 族无按需加载，且不忽略这个字段。对策：延迟标记只在支持的族的 adapter 里拼，跨族共享的工具定义里不放。
70. **DashScope `web_extractor` 单独声明被拒。**
    现象：② 面 HTTP 200 后首个事件 `response.failed`（`must be executed with web_search tool`）。
    对策：抓取存成搜索的附加档，单独出现时归一化丢弃，发送前再归一化一次。
71. **OpenAI 搜索的 `open_page` 被当成 search 解析 → 日志里一串空查询空结果。**
    原因：`open_page` / `find_in_page` 只带 `url`，没有 queries / sources；`search` 有时只给单数 `query`。
    对策：按 `action.type` 分支解析，queries 缺失退回 `query`。

## H. 可观测性与实测方法（详见 06 §4.2、§8）

72. **包装层装日志钩子时替换了调用方的钩子 → 调用方静默收不到回调。**
    现象：live 实测里所有请求体断言读到 `undefined`，一半"失败"不是端点的错。
    对策：包装一律串联 `own(x); caller?.(x)`，单测钉住调用方钩子仍被调用。
73. **live 实测"全部 skipped"被当成通过。**
    原因：`describe.skipIf(!KEY)` 在 key 没进 env 时静默全跳；key 写在交互 shell 的配置文件里，
    工具/CI 的非交互 shell 不加载。对策：0 passed 即查 env；每条命令经登录 shell 或显式 export 加载 key，key 不进仓库。

## I. 千问服务端工具（代码解释器 / 网页抓取，详见 05 §5「代码解释器」）

74. **开了网页抓取（或代码解释器）的千问模型，agent 运行第一轮就 400。**
    现象：`Agent mode does not support tools. You need to either avoid using enable_code_interpreter or avoid using the agent mode with enable_search.`
    原因：① 面的 `search_strategy:"agent_max"` 与 `enable_code_interpreter` 都是 DashScope 的「agent 模式」，和函数工具同发必 400；
    接入时只测了不带工具的请求，于是每个带工具的轮次都炸，而单测全绿。
    对策：本轮带函数工具时两者都不发（抓取退回普通 `enable_search`，带工具实测正常）；实测套件里至少一条「带函数工具 + 服务端工具」的用例。
75. **① 面给不支持的模型开代码解释器 → 不报错、答案没算过。**
    原因：qwen-max、qwen3-max-preview 等静默忽略 `enable_code_interpreter`（prompt_tokens 不变），另一些（qwen3.8 全系）才 400。
    对策：按 wire × 模型 id 的实测正则表放行，UI 只对匹配 id 显示开关；实测用「答案模型背不出来」的题（如 123²¹ 的 44 位数）判断真跑没跑。
76. **② 面关思考 + 代码解释器 → HTTP 200 后 `response.failed`。**
    原因：`Normal mode does not support Code interpreter. Please set enable_thinking to true.`；① 面关思考却照常跑，两面条件相反。
    对策：② 面 `reasoning.effort` 为 `none` 时本轮不发这个工具；没设档位（端点默认思考）照常发。
77. **辅助请求继承了模型行上的服务端工具 → 每次摘要/翻译都在静默多花钱。**
    原因：服务端工具权限挂在模型配置、随连接参数带进每个请求；摘要、合集摘要、翻译、图片描述这些 app 自己发起的请求也就带上了搜索和代码解释器
    （后者光说明约 800 输入 token/请求，还会多轮推理），且完全无症状。
    对策：每个非对话调用点显式覆盖为空（与结构化任务、历史压缩一致），用源码扫描或 mock 断言守住，并确认删掉覆盖时测试会红。
78. **代码解释器画的图，链接存下来半天后就打不开。**
    原因：图片以 markdown 图片写在 `logs` 里，指向带签名的 OSS 地址，约 12 小时过期；最终回答正文里也不带这个链接。
    对策：只当文本记进执行日志；要留图就在过期前下载成本地文件（同 13 篇 §6：存链接的图库会静默腐烂）。

## J. 字节跳动 · 火山方舟 Seedream（详见 13 §4.1、01 §9.3）

79. **Seedream 出的图右下角都带「AI 生成」字样，用户以为是模型画的。**
    原因：`watermark` 上游**默认 `true`**，请求里不写就加水印，照常计费；OpenAI 系客户端没有这个字段，自然不发。
    对策：ark route 恒明发 `watermark`，UI 默认关；单测断言 body 里 `watermark === false`。
80. **套餐渠道保存后再打开，地址被「恢复」成按量 base，之后每次调用 401。**
    原因：按量 `/api/v3` 与套餐 `/api/plan/v3` 是同一 channel type 的两个变体，编辑器只按 type 回读变体，
    落到首个（按量），随即按变体默认地址改写 endpoint；两个 base 的 key 互不通用。
    对策：变体按 endpoint 回读（去尾斜杠比对），都不中才落回首个；单测覆盖两个 base 与自定义地址。
81. **套餐 key 下模型「不存在」，按量文档里的 id 明明写着。**
    现象：`doubao-seedream-5-0-260128` 与 4.5 / 4.0 回 `404 UnsupportedModel`；`GET /models` 也是 404。
    原因：套餐只服务 5.0 pro / lite，且认 `…-5.0-lite` 或带 `lite` 的日期 id，不认按量文档里不带 `lite` 的正式 id；套餐没有模型列表。
    对策：静态目录同时收两种拼写，发现遇 404 退回目录；拿不准时用非法 `size` 零成本探测（400 = 支持，404 = 不支持）。
82. **组图/图层请求画到一半被客户端判超时，钱照扣、图没收到。**
    原因：接口仅同步，一次请求等全部图画完；单张 26–43 s，组图最多 15 张，固定 3 分钟超时必炸。
    对策：超时按本次请求可能画的张数放宽（+40 s/张、封顶 15 分钟，拆图层按 17 张算），单测钉住公式。
83. **按 token 计价的费用组给 Seedream 算出一笔离谱的钱。**
    原因：`usage.output_tokens` = 像素/256（2K 一张 ≈16K），只是参考值，账单按 `generated_images` 按张计；
    把它映射进通用的 output_tokens 键，token 计费就当真了。
    对策：张数进 image_count，方舟 usage 原样放私有元数据键只展示；单测断言 token 键不存在。
84. **组图里一张被审核拦下，整次请求被判失败，其余已计费的图全丢。**
    原因：`data[]` 允许单项是 `{error:{code,message}}`（`OutputImageSensitiveContentDetected`），其余项正常；
    按「有 error 即失败」处理就把成功的图一起扔了。对策：收下成功项、报失败张数；只有一张都没有时才抛（顶层 `error`）。

## K. 出图的逐家形状、流式与结构化结果（详见 13 §4.1「流式出图」、§4.2、§6、§8）

85. **流式出图第一张还没画完，客户端就判「连接空闲超时」，已计费的一组全丢。**
    原因：Seedream 的 SSE 响应头要等第一张画完才回来（≈27 s，4K 更久），聊天的首块 120 s 守卫按文本流设计。
    对策：出图流首块与后续块都按单图期限计（参考 5 分钟），首块超时判期限、不重试。
86. **`stream:true` 请求回了 400，解析器却在等 SSE，报了个莫名其妙的解析错误。**
    原因：参数校验失败不走 SSE，回的是普通 JSON 错误信封。对策：200 时看 body 首行判断 SSE 还是 JSON，非 200 按
    同步错误读；别信 `Content-Type`。
87. **组图流里一张被审核拦下，整个流被判失败，之前到的图也扔了。**
    原因：`partial_failed` 事件带 `error` 对象，通用的「有 error 字段即失败」信封检查把它当请求级错误。
    对策：只对不认识的事件做信封检查；`partial_failed` 只记一张失败。并且边到边存、按已送达张数记用量。
88. **拆图层的名字 / 框挂到了别的图层上，画布上每层都错位一格。**
    原因：批量解析图片引用时跳过了下载失败的一项，后面的图与按位置对齐的属性错位；或者属性放进了跨 chunk 合并的 metadata。
    对策：逐图属性用类型化字段、与图同 chunk；逐项下载保位置（失败位置留空或整组失败）。
89. **用户在应用里改了名，图层角标和画布都没了。**
    原因：图层表以文件路径为主键，改名 / 移动 / 文件夹搬运没带着行走（或覆盖写同名文件留下了旧行）。
    对策：所有应用内文件操作调 `move`（文件夹按前缀）/ `forget`；覆盖前先删目标行；读取时过滤不存在的文件。
90. **MiniMax 出图「成功」但图库里什么都没有；审核拦截从不报错。**
    原因：两层失败——`base_resp.status_code≠0` 在 HTTP 200 里；逐图失败在 `metadata.success_count==0`，而这个计数
    **是字符串** `"0"`，按数字判永不命中。对策：两层都查，计数两种类型都认；零张即抛错。
91. **MiniMax 「改图」返回一张和原图毫不相干的新图。**
    原因：`subject_reference` 是主体（人物）参考，不是编辑；这条 wire 上没有编辑操作。
    对策：caps 声明 `edit:false`，UI 写明「主体参考」，不要把它挂在「编辑」入口下。
92. **中继经 chat 出图，一张图存成了三个文件；或者一张都没存、「模型只回了文字」里引用了 200 字 base64。**
    原因：同一中继把同一张图同时放在 `content`（裸 base64）、`images[0].b64_json`、`image_b64_json`；另一时刻整条回复
    就是裸 base64 / 裸链接，没有 `data:` 前缀也没有 markdown。对策：接住所有形状，按字节 SHA-256 去重；裸内容
    过两道闸（裸链接仅限出图模型；裸 base64 ≥64 字符且 magic bytes 是图片）。
93. **OpenAI 兼容的改图接口对单张图 400，多张却正常（或反之）。**
    原因：multipart 字段名 `image[]` 是新写法，dall-e-2 的编辑与照它写的中继只认单数 `image`。
    对策：字段名跟张数走——1 张 `image`、多张 `image[]`；每个文件 part 显式带 `Content-Type`。

## L. 智谱 BigModel（详见 03 §3.1、04 §2 / §4、05 §5「服务端工具归平台」、06 §2、01 §9.4）

94. **GLM 的「关闭思考」开了也没关，推理照想、照计费。**
    原因：按 ① 族默认发 `reasoning_effort:"none"`。glm-4.x / 5 / 5-turbo / 5.1 对任何 effort 值都 200 并静默丢弃；glm-5.2 收下
    `none` 却照样思考（文档说它放弃思考）。对策：关思考发 `thinking:{type:"disabled"}`；5.3 代关不掉，UI 不给「关」。
95. **GLM 的思考档位拨了没有任何变化。**
    原因：4.x / 5.0 / 5.1 静默丢弃 `reasoning_effort`；5.2 把 low / medium 折成 high、xhigh 折成 max。对策：旧代只给开关，5.2 只给
    high / max 两档，只有 5.3 代给 low / high / max。
96. **结构化抽取在 GLM 上第一轮就失败，报「API 调用参数有误」。**
    原因：强制 `tool_choice`（具名）在 glm-4.7 / 4.6 / 4.5 思考开时 400，文案不提 `tool_choice`，按参数名识别的降级重试认不出。
    对策：该平台上 forced 一律发 `auto`，由回退链兜底（04 §4）。
97. **强制调用工具在 GLM 上「成功」了，模型却只回了一段文字。**
    原因：5.x 与 4.7 对 `required` / 具名都 200 但不强制（文档：只支持 `auto`）。对策：同 96；调用方必须把「没调工具」当回退信号。
98. **声明了 `json_schema`，GLM 回的是代码块包着的文本，字段名还是中文。**
    原因：智谱 200 但静默无视 `json_schema`（文档只列 `text` / `json_object`）。对策：`json_schema` 只对实测过的端点放开；此处用 `json_object`。
99. **GLM 回答写到一半停了，界面当成正常结束。**
    原因：流式中途失败只在 `finish_reason` 里送达（`network_error`；审核是 `sensitive`，不是 `content_filter`）。对策：两者 throw，
    `sensitive` 进安全拦截记忆；`model_context_window_exceeded` 记截断。
100. **开了 GLM 的联网搜索，回答说「根据联网搜索结果」，其实一次都没搜。**
    原因：对话内 `web_search` 工具默认做搜索意图识别，意图不够就跳过，模型的话术不变；响应里没有 `web_search` 字段。
    对策：发 `search_intent:false`；以响应顶层 `web_search[]` 是否存在判定「真搜了」，不信回答里的措辞。

## M. 千问 / 万相出图的信封与尺寸（详见 13 §4「自由尺寸的规则」）

101. **wan2.7 出图每次都 400，qwen 走同一条路却正常。**
    现象：`400 InvalidParameter: Field required: input.messages`【实测 2026-09-19，wan2.7-image-pro】。
    原因：按一份二手文档镜像给 wan 另写了一种形状，把 `messages` 放在顶层；真实端点对两个家族用同一个
    `{model, input:{messages}, parameters}` 信封，差别只在 content 里图和文谁在前。
    对策：只保留一种信封，part 顺序由模型的参数表声明；单测断言 `input.messages` 存在、顶层没有 `messages`。
    对照上游官方页核对嵌套层级，不要只看镜像或仓库内笔记。
102. **千问 / 万相出图贵了一倍，图也比预期大。**
    现象：没有任何报错，出图 2048²，账单落在 2K 档【外部实测 2026-09-04】。
    原因：请求里没写 `size`，两家的缺省都是 2K 档；qwen 改图省略 `size` 时也会把输入放大到 2K 面积。
    对策：有 `size` 控件的模型永远显式发（qwen 发 1K 面积内的值，wan 发 `"1K"`）；
    基础版 `qwen-image-edit` 没有这个参数，发了反而 400，要按模型参数表决定发不发。
103. **换模型或重试时出图 400，报尺寸格式或范围不对。**
    原因：任务参数比选它的模型活得久。留下来的 `auto`、`"2K"`，或另一个模型合法的像素值，原样转发到了
    规则不同的模型上：qwen-image-3.0 不收关键字，初代 `qwen-image` 只收五个固定值，改图 max/plus 按单边限。
    对策：发送前用目标模型的规则校验，不合法就换成该模型的默认值；规则按模型写成数据（面积区间或单边区间、
    比例上限、步长），不要写成按模型名分支的代码。
104. **选了官方推荐的 16:9 尺寸，界面却显示成「自定义比例」。**
    原因：wan 官方的 2K 16:9 格子是 2688×1536，也就是 1.75:1，不是精确的 16:9；按精确比例反查芯片查不到。
    对策：反查比例芯片时留容差（参考值 3%），认出芯片后改用芯片的精确比例继续计算，档位轴才能找回官方格子。

## N. ① 中转的接收侧畸形、探测与视频补遗（详见 02 §2.2、§3.2、§7.2，03 §3.2、§4，05 §3，06 §1、§5，13 §4.2，14 §2）

来源：Joycai Image AI Toolkits 的线上流量与修复记录（2026-08 至 2026-09）。

105. **工具以空参数执行，模型说「我已经按你的要求调用了」。**
    现象：不报错，工具拿到 `{}`【实测 2026-08-08，经中转的 Claude 后端】。
    原因：`function.arguments` 是背靠背拼接的多个 JSON 对象（`{}{"id":1}`，先吐空对象占位），解析失败后兜底成 `{}`。
    对策：解析失败时按括号深度切出顶层对象、左到右合并；只切出一个对象才算真非法（05 §3）。
106. **第二轮请求被拒，报重复的 `tool_call_id`；之后整段会话每轮都 400。**
    原因：中转把调用 id 发成 `""` 而不是缺失，`id ?? "call_"+i` 留下空串，同批两个调用共用空 id；历史是累积的，每轮重发。
    对策：空串按缺失处理，按序号补 id【实测 2026-08，中转流量】。
107. **经中转的推理模型不再显示思考，回传时字段名也错了。**
    原因：同一个 delta 里既有 `reasoning_content:""` 又有非空的 `reasoning`，`a ?? b` 取到空串。
    对策：按候选表逐个试，取第一个**非空字符串**并连字段名一起记下【实测 2026-09-14】（03 §4）。
108. **所有 ① 流式请求的 token 用量都是 0，没有任何报错。**
    原因：`include_usage` 的末块是 `"choices": []`，`choices?[0]` 挡不住空列表、抛越界异常，被「坏行就跳过」的 catch 吞掉，
    usage 跟着一起丢了【实测 2026-08-14，Joycai 修复】。
    对策：取首个 choice 前判空；usage 在 choices 之外单独读；容错 catch 只罩 JSON 解析，不罩整块处理（02 §3.2）。
109. **工具已经把结果交付了，这一轮却显示「模型没有返回内容」而失败。**
    原因：GPT-5.x（② Responses，经中转 gpt-5.6）在工具结果之后以一个文本为空、`status:"completed"`、`phase:"final_answer"` 的
    message 条目收尾，空回复守卫只认非空输出【实测 2026-09-15】。
    对策：服务端标了 completed 的 message 条目算输出；没有任何条目的 200 才是坏响应（02 §7.2）。① 族不适用。
110. **出图模型经中转的 chat 路由一律 400：`images[0] must be an http/https URL or image data URI`。**
    原因：中转把这次 chat 调用翻译成出图请求，只认 part 数组形的 `content`，纯文本的字符串形被当成图片地址校验【实测 2026-09-05】。
    对策：声明为出图的模型，纯文本也包成单元素 `[{"type":"text",…}]`；对话模型保持字符串（13 §4.2）。
111. **经中转的 Gemini 看不见附图、也不理系统提示，照常 200。**
    原因：请求用了 snake_case（`inline_data` / `mime_type` / `system_instruction`）；Google 两种都收，New API 的 ③ 面只认 camelCase、
    无视未知键【实测 2026-09-05】。
    对策：③ 请求键一律 camelCase，测试遍历整个 payload 断言无下划线结构键（02 §2.2）。
112. **连接测试显示「已连通」，但每个真实请求都失败。**
    原因：欠费的中转对任何请求回 402，且是完整的协议形 JSON 错误——恰好是完成探测判「连通」的形状【实测 2026-09-05】。
    对策：402 在探测的任一步都报不可达并附提供方原文；也不要报成鉴权失败（06 §5）。
113. **MiniMax 视频「成功」出片、照常计费，但完全没用首尾帧。**
    原因：媒体项写成平铺的 `url`；端点照收、当作没附图生成。正确形状是嵌套的
    `{"type":"image_url","image_url":{"url":…},"role":"first_frame"}`【实测 2026-08-29】。
    对策：按嵌套形状发，另带一个 text 项；验收判据是出片遵守首尾帧，不是 HTTP 200（14 §2）。
114. **火山方舟的豆包模型「关了思考」照样在想、照样计费。**
    原因：给它挂了千问的 `enable_thinking:false`——方舟把未知字段静默忽略【实测 2026-09-18】。
    对策：方舟用 ① 默认的 `reasoning_effort:"none"`（实测 0 推理 token），不声明方言；方言按厂商声明，不按「都兼容 ①」复用（03 §3.2）。


## O. 语音识别（详见 16 篇）

来源：pyVideoTrans 的 Flutter 重写版（subtitle_studio）与原 Python 版，2026-09。

115. **开了说话人分离，字幕里一个编号都没有，请求照常 200。**
    原因：百炼同步接口（`qwen-audio-3.0-asr-flash` / `fun-asr-flash`）收下 `diarization_enabled: true` 后静默忽略；文档写着支持【实测 2026-09-13】。
    对策：分离只走 `-filetrans`（`qwen-audio-3.0-asr-flash-filetrans` 实测可用）；开始前按模型提示，结果里没编号时提示而不报错（16 §7）。
116. **整段 25 秒只出来一条字幕，或者整个文件只有一条。**
    原因：百炼同步接口不返回句级时间戳【实测】；`gpt-4o-*-transcribe` 不给 `segments`【文档】。
    对策：同步接口的时间码来自切片位置（16 §4.1）；没有 segments 的兜底要靠统一的按字数拆分（16 §6.2），并告诉用户时间码是估算。
117. **相邻两条字幕开头结尾重复了半个词。**
    原因：切片时为了「留余量」多截了邻段 200 ms 真实音频，邻段的词被识别了两次【实测，2026-09-13 修复】。
    对策：片外补的是静音（`adelay` + `apad`），时间码仍用原切分点（16 §4.1）。
118. **一段背景音乐让整个识别任务失败。**
    原因：百炼对没人声的片段回 `400` + `ASR_RESPONSE_HAVE_NO_WORDS`【实测】，被当成请求错误。同类：一片被内容审核拒掉回 400 / 422 + `DataInspectionFailed`【实现】。
    对策：前者按空文本成功；后者只跳过这一片，其余照常（16 §8、§10.2）。
119. **filetrans 续跑时反复报鉴权失败 / 找不到，其实密钥没问题。**
    原因：把 403 / 404 当成全局致命错误。OSS 上传 403 是凭证过期；下载结果 403 / 404 是签名地址过期；轮询 404 是任务不在了。
    对策：按「哪一步」分类，各自回退一步：重取凭证 / 丢 taskId / 丢 fileUrl（16 §8 表）。
120. **Dart 上传到百炼 OSS 回 `MalformedPOSTRequest`，文档里找不到原因。**
    原因：`http` 包 `MultipartRequest` 生成的正文 OSS 不认（boundary 字符、part 头小写、头顺序三处差异之一，未定位）【实测 2026-09-13】。
    对策：手拼 multipart：boundary 只用字母数字、规范大小写的 `Content-Disposition` 在 `Content-Type` 前、`file` 放最后；上传不带 `Authorization`（16 §5）。
121. **识别任务中途限流停下，续跑却从头开始、重新计费。**
    原因：续跑判断检查点可用时要求「段数相等」，而中途停下时后面的段还没记录【实测，2026-09 修复】。
    对策：记录过的每一段都能在新切分里找到相同起止就沿用（16 §9）。
122. **火山豆包识别「成功」了，却一个字都没有。**
    原因：成败在响应头 `X-Api-Status-Code`（`20000000` 才成功，`20000003` 是静音），HTTP 状态恒为 200；只看 HTTP 状态就放行了【实现】。
    对策：先读这个头再解析 body；缺头也按失败（16 §10.2）。同类的「HTTP 状态之外的第二层判据」见 06 §2。

## P. 出图计费：xAI 质量档、上游报价、输入图（详见 13 §4.2「xai-images」、§7，06 §1「第四种口径」，14 §2「xAI 实测」）

123. **不发 `quality` 的 xAI 出图按 Medium 计，本地按标价表第一行（Low）估。**
    现象：账单比应用记的高三分之一，没有任何错误。原因：`grok-imagine-image-2.0` 六格按 分辨率 × 质量 标价，`quality` 缺省 = medium
    （$0.06），客户端只发 `resolution`、本地表按第一行 Low（$0.04）算【实测 2026-09-22】。
    对策：默认值明发（`quality: "medium"`），用量行才带得上规格；本地估价与回包的 `cost_in_usd_ticks` 对照（13 §7）。
124. **`quality: auto` 让模型定档，账单不可预算。**
    现象：同一请求两次价格不同（一次实测选了 Low）。原因：档位由模型决定，按规格计价的表写不出它【实测 2026-09-22】。
    对策：UI 不提供 `auto`；若上游报钱（坑 127 的字段）就按报价记，不按表。
125. **初代 `grok-imagine-image` 默默收下 `quality`，`1.5k` 却 400。**
    现象：发 `quality: low` 200、价格不变（$0.02 平价，`/v1/image-generation-models` 里 `pricing: []`）；发 `resolution: 1.5k`
    → 400 `1.5K resolution is not supported for this model.`【实测 2026-09-22】。
    对策：能力表按 id 尾巴分流：初代不给质量控件、尺寸只 1k / 2k；共用一份参数记忆的家族要在发出前把别的型号选过的 `1.5k` 回落到默认。
126. **上游同名字段改写了你的记账键。**
    现象：某中转的 `usage` 里恰好有个与你内部中性键同名的字段（`input_image_count` / `reported_cost_usd` 或你自己起的名），原样铺进
    metadata 后成了账——报价键压过整张表，张数键让文生图收参考图的钱。原因：记账层对所有厂商一视同仁地读中性键，而聊天四族与
    images 各家都把上游 `usage` 原样铺进 metadata【实现，Joycai 2026-09-22 两轮 review 才堵全八处；同日第九处：Veo 的视频轮询
    把上游 operation body **整个当内部信封**返回，执行器从信封读报价键，保留键随整个 body 穿透——那里没有 spread，按「找铺 usage 的地方」
    自查查不到它】。
    对策：所有原样铺上游 map 的地方走同一个剔保留键的函数；只有协议自己的换算能写这两个键、且写在铺之后；每处一条伪造用例。
    除了「铺 usage」，还要查「把上游 body 整个当内部信封返回」的路径（异步作业的轮询最常见）：要么自造信封，要么返回前 remove 掉保留键。
127. **上游报价只在收尾块，流被放弃就退回表算。**
    现象：出图流在图片到达后被取消 / 空闲守卫掐断，用量行按档位表记而不是按上游报价。原因：`cost_in_usd_ticks` 翻成的中性键只挂在
    收尾块的 metadata 上，提前退出的记账只看到图片块【实现，Joycai 2026-09-22】。
    对策：图片块携带报价与张数（与 `input_image_count` 同一做法，13 §4.1「流式出图」、§7）。
128. **xAI 参考图上限：文档 3 张，实测 5 张 200 并计费。**
    现象：按文档把上限写 3，用户第 4、5 张被截掉；上游其实收。原因：文档与实测不一致【文档 3；实测 2026-09-21 五张 200、
    `cost_in_usd_ticks` = 0.06 + 5 × 0.01】。对策：上限 5；`n:2` 时输入图按请求收一次不乘张数（13 §7）。
129. **视频按秒标价，参考图另收钱，标价页没写；报价只在终态回包。**
    现象：按「$/秒 × 秒数」估的视频账每条比账单少几美分，无报错；把「输入图」一侧只开给按张计价的组，按秒 / 按条的组根本没处填。
    原因：xAI `grok-imagine-video-1.5` 首帧 `image` 与 `reference_images` 每张 +$0.01（1 s · 480p：文生 0.08、首帧 0.09、两张参考
    0.10），页面只写 $0.080/s；`usage.cost_in_usd_ticks` 只在 `GET /v1/videos/{id}` 的 done 回包里，提交回包没有【实测 2026-09-22】。
    对策：输入图单价对按秒 / 按条的组同样开放，视频协议发布实际放进请求体的张数（14 §1 的 media 列表数完再发）；提交时按请求秒数记，
    终态用报价**改写整行的报价列**，不是只改秒数（14 §3.8）。

## Q. Seedream 透明背景与输入图上限（详见 13 §4.1「5.0 pro / flash 的透明背景」）

130. **透明底立绘「加上背景」照常 200、照常计费，背景还是透明的，背景画进了人物里。**
    原因：`background:"transparent"` 保证的是结果背景透明；「要一张填满的背景」与之矛盾，模型不报错，折中成在主体
    轮廓内画背景【实测 2026-09-23】。按「输入是透明 PNG 就开」自动判定，恰好把这类改图弄坏。
    对策：开不开交给写指令的一方（agent 工具参数 / UI 选项，默认保留），只在改图时开；改色、改姿势可以保持开
    （主体可变形，实测箭头改向照样是抠图）。
131. **改图带满参考图，用户批准后才 400「cannot exceed 10」。**
    原因：上限数的是全部输入图，被改的源图和参考图走同一个 `image` 字段；只数参考图的校验放过了「源图 + 满额」。
    对策：校验「源图 ? 1 : 0 + 参考图数」≤ 上限，在出审批卡之前拒；报错里说明「含被改的图」。
    同类：设置界面按表单重建能力字段时，没有控件的上限（起步行的 10 / 14）会在一次保存后静默消失——沿用原值，
    且只在线路与方言都没变时沿用（错的上限比没有更糟）。
132. **透明编辑对一张「带透明通道」的 PNG 报 400「at least one transparent pixel」。**
    原因：上游解码判定是否真有透明像素；PNG 头部的 color type 6 / 调色板只说明「可能」。全不透明的 RGBA 导出图、
    无 tRNS 的调色板图都会被拒【实测 2026-09-23，三种都是同一条 `param:"image"` 文案】。
    对策：这条 400 出图前、免费——去掉 `background` 与 `output_format` 重试一次（结果与普通改图相同），
    只匹配这条文案，别的 400 不重试；不必为此在客户端全量解码。

## R. 火山方舟豆包对话：加密推理与签名、按模型的 schema、探测误判（详见 03 §3.2、04 §2、01 §9.3、06 §5）

133. **豆包 2.1 的多轮工具调用越做越差，没有任何报错。**
    原因：2.1 系的 `reasoning_content` 只是思考摘要，原文加密在 `encrypted_content`；适配器只按字段名收 `reasoning_content` 回传，
    密文丢了，模型改在摘要上推理（厂商：「推理效果下降」）。功能用例照样全过——这正是它难发现的地方【实测 2026-09-23】。
    对策：① 流解析把 `encrypted_content` 整串留存（按到达顺序拼接，不显示），工具轮与摘要一起回传；载体带 modelId，换模型剥离。
134. **给豆包声明了 `json_schema`，结构化结果「合法 JSON」却不合 schema，200。**
    原因：同一平台上 2.0-lite 在 ① strict 与 ② 都不守 schema，2.1-turbo 守；2.0-mini 在 ② 多出字段【实测 2026-09-23】。
    对策：按模型前缀放行 json_schema，其余留 `json_object`；验证时用「schema 与 prompt 冲突」的用例（enum 只许一个值、禁额外字段）——
    只看输出能否解析证明不了约束生效。
135. **火山方舟套餐被判定「没有 Responses 接口」，其实有。**
    原因：② 在 `…/api/plan/v3/responses`，探测打在少了 `/v3` 的 `/api/plan/responses` 上得 404，据此把整个面漏掉【实测 2026-09-18】。
    对策：探测路径与 ① 同 base 推（`{①的 base}/responses`），404 先怀疑路径拼错再下结论；厂商文档的服务端工具页常是另一个线索。
136. **连接测试说套餐 key 无效，但对话照常能用。**
    原因：套餐 ④ 面 `/v1/models` 对有效 key 回 401（该前缀没有模型列表）；按「/models 401 = 鉴权失败」判就误报【实测 2026-09-18】。
    对策：`/models` 404 / 401 / 403 都再发一次最小补全（不存在的模型名，不计费），由补全端点的 401 与协议形状 404 定论（06 §5）。
137. **豆包 2.1 在 Anthropic 面丢了或改坏了 thinking 签名，工具轮照样 200。**
    原因：火山 ④ 面的 2.1 系 thinking 块带 `signature`（2.0 系没有，所以按旧实测会以为「这家不用签名」）；上游不校验，
    原样、篡改、删掉签名回传都 200——与 Anthropic 官方文档口径的 400 相反，错了不会响【实测 2026-09-23】。
    对策：④ 一律整块原样回传（含 `signature_delta` 拼出的签名），不要按「这家没签名」做特判或只回 `thinking` 文本；
    验证只能看适配器存下的块里签名在不在，不能靠第二轮是否报错。

## S. 中转站翻译层：Kiro 渠道的 Claude（详见 01 §9.2、02 §1 表后、03 §3.3、04 §2 / §4、05 §5「中转站自己做服务端工具」、06 §1 / §8）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十五个样本、`live.relay-kiro.test.ts`（一台 New API 中转站，`[特价kiro量]claude-opus-4-6` / `-opus-5`，① ④ 两族）。
后端是 AWS Kiro、不是 Anthropic API，中转站在中间翻译——**下面每一条都是 200、不报错**。同一端点 `max_tokens` 无视见坑 65 同形、签名不校验见坑 137 同形。

138. **强制 `tool_choice` 用 curl 试过是好的，应用里模型却从不调用工具。**
    原因：中转站只在**非流式**转换路径上实现了强制；流式下 ④ `any` / `tool` 32 次里 1 次调用、① `required` / 具名 4 次 0 次，
    模型只回散文。同一请求流式 `prompt_tokens` 301、非流式 102——两套转换【实测 2026-09-23】。curl 探形状多是非流式，应用永远流式。
    对策：实测按应用实际走的路径做（06 §8 第 7 条）；被点名的模型 id 上 forced 一律发 `auto`，由结构化回退链兜底（04 §4「第四种变体」）。
139. **开了联网搜索，回答变成一页「Here are the search results for "…"」，写作指令没人理。**
    原因：只挂 `web_search`、不带函数工具时，中转站**劫持整条请求**——拿第一条 user 消息原文当搜索词，返回模板 + 结果块，模型根本没跑
    （两款模型逐字相同，`output_tokens` 固定 644 / 568 / 478）；① 的 `web_search_options` 同样被劫持。与函数工具同发时流式真搜、非流式被丢【实测 2026-09-23】。
    对策：对这个渠道的 id 不发 `web_search`，或只在本轮带函数工具且流式时发；服务端工具按「单独 / 同发 × 流式 / 非流式」四种组合实测（05 §5）。
140. **① 面选了「最高」思考档，模型反而不想了。**
    原因：这台中转站把 `reasoning_effort` 的 `low` / `medium` / `high` 翻成思考，**`max`、`none`、乱写的值都翻成不想**；
    顶层 `thinking` 也被忽略；`reasoning_tokens` 恒为 0，看 usage 也看不出【实测 2026-09-23】。
    对策：作者说明写「别选最高」，或对被点名的 id 把 `max` 夹到 `high`；判断有没有想看 `reasoning_content` 有没有文本（03 §3.3）。
    **（2026-09-23 更正：不是 Kiro 特有——同台 CC / anti / AWSb 的 Claude 也一样，是这台 New API 的 ①→④ 转换；夹 `max` 的范围应是整台的 Claude，见坑 147。）**
141. **④ 面调 effort、调 `display`，输出看不出任何变化。**
    原因：`output_config.effort` 只有 `low` 有效果，medium / high / max 输出量都 ≈ 1,050 token；乱写的 effort 也 200；
    `display:"omitted"` 照样返回完整思考原文；`budget_tokens ≥ max_tokens` 也 200【实测 2026-09-23】。
    对策：UI 说明写清这个渠道只有「关 / 开」两态，不为此改翻译表；thinking 块仍整块原样回传——签名不校验，回传错了不会响（03 §3.3、坑 137）。
142. **声明了 JSON mode / json_schema，结果仍是 markdown 围栏里的自拟键名。**
    原因：① `response_format`（`json_object` / `json_schema` strict）与 ④ `output_config.format`、`output_format` + beta 头全部被静默无视；
    ① 的 cue 又是条件追加，以为原生约束在就没补【实测 2026-09-23】。
    对策：这类 id 的结构化能力判「不发」、解析成 cue-only（恒发 cue + `extractJsonObject` 抠围栏）；用 schema 与 prompt 冲突的用例验证（04 §2）。
    **（2026-09-23 更正：① 那一半四个渠道都一样、是转换层的；④ 那一半才随渠道，见坑 150。）**
143. **PDF 附件发出去了，模型说「没看到文档」，而且这一条慢了十倍。**
    原因：④ `document`（base64 / url）与 ① `file` 片段都被静默丢弃，那条请求 33 s（别的 3 s）；URL 形态的图片也被丢，只有 base64 / data URL 图片送得到【实测 2026-09-23】。
    对策：这个渠道的 id 判 `pdfInput` 不发，PDF 交给别的模型；图片一律内联 base64；验证用模型猜不出的内容看答案（02 §1 表后）。
144. **模型说它抓了网页、跑了代码，其实什么都没执行。**
    原因：`web_fetch_20250910`、`code_execution_20250825`、造的 `type` 全部 200 且被丢，模型编出 `<h1>Example Domain</h1>`、一段没跑过的 Python 和「输出」【实测 2026-09-23】。
    对策：「执行了没有」只凭响应里的 `server_tool_use` / `*_tool_result` 块判断，执行日志与 live 用例都断言块存在，不凭正文（05 §5）。
145. **打了 `cache_control` 反而更贵，用量页的缓存命中数也对不上。**
    原因：同一 7.4k 前缀连发两次，两次都报 `cache_creation_input_tokens: 7360`，`cache_read` 永远只有几十——只写不读；
    不带 `cache_control` 的请求也报几十 token 的 `cache_read`，usage 的缓存分段是中转站估算拼出来的【实测 2026-09-23】。
    对策：兼容 ④ 线路默认不发 `cache_control`；这类端点的缓存成本标为估算，验证缓存看第二次 `cache_read` 是否接近前缀长度（06 §1）。
146. **在中转站上给一个渠道的模型关掉能力，同一台上别的模型也全变成「未实测」。**
    原因：用了「`runs` 白名单 + 名单外 = 未实测」的模型格；中转站没有可识别的主机，渠道只在 id 里，这种格子把同一台上所有没列名的模型一起拉下来【实现 2026-09-23，capability-gating-plan §8.10】。
    对策：只写 `refuses` 的格子**只点名**（`/^(?=.*kiro)(?=.*claude)/`），名单外的 id 照常走平台规则；查能力表的每个调用点都带模型 id，
    用「矩阵 vs 适配器实发 body」的一致性测试兜住（01 §9.2）。

## T. 同一台中转站、同一个模型、不同后端渠道（详见 01 §9.2「五个渠道五种阉割法」、02 §1 表后、03 §3.3、04 §2 / §4、05 §5、06 §1 / §8）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十六个样本（一台 New API，`claude-opus-4-6` / `-opus-5` 挂在 Kiro / CC / anti 三个反代与 AWSb 正向下，① ④ 两族）、
`docs/issues/relay-claude-channel-gating.md`。**中转站上能力的主键是（平台, 面, 渠道, 模型）**；渠道只写在 id 前缀里，反代渠道的缺口一律 200。

147. **只测了中转站的一个渠道，把转换层的缺口记成了渠道特性（或反过来）。**
    原因：第十五个样本只测了 Kiro，把 ① `reasoning_effort:"max"` = 不想、`response_format` 被丢记成 Kiro 特有；测到 CC / anti / AWSb 才发现四个渠道一样，
    是这台 New API 的 ①→④ 转换【实测 2026-09-23】。归属错了，裁决就错：按渠道点名会漏掉整台的其余 Claude，按平台写又会误伤真正的渠道差异。
    对策：同一台至少测两个渠道；都一样的归转换层（平台 × 面），不一样的归渠道（06 §8 第 9 条）。改归属时保留旧结论并注明被哪次实测推翻。
148. **思考档位拨满，模型一个字都没想，哪都不报错。**
    原因：anti 渠道的 Claude 根本不思考——④ `thinking` 的任何写法、`effort`、① `reasoning_effort`、`-thinking` 变体全部无效，响应里没有 thinking 块【实测 2026-09-23】。
    对策：思考能力按渠道声明（01 §9.2 第 7 条），不从「这是 Claude」推出；验证看有没有 thinking 块 / `reasoning_content` 的文本，不看请求发了什么（03 §3.3）。
149. **按思考计费，思考面板却永远空白。**
    原因：CC 渠道的 opus-5 返回 thinking 块但文本恒为空——带 `display:"summarized"`、难题上 765 输出 token 也空；同渠道 opus-4-6 有文本；① 面同样没有 `reasoning_content`【实测 2026-09-23】。
    对策：不是 `display` 发错了、也不是解析 bug，别去改读取逻辑；按（渠道, 模型）记下，UI 在「块在、文本空」时说明「该渠道不返回思考内容」。
150. **同一个模型、同一个渠道，④ 面结构化输出好好的，换 ① 面就不灵。**
    原因：AWSb（Bedrock 正向）④ `output_config.format` 执行 schema；① `response_format` 被 New API 的转换丢掉。④ 面本身也随渠道：Kiro / anti 无视，CC 只有 opus-5 执行【实测 2026-09-23】。
    对策：能力格按面分——① 面的 `structuredOutput` 按平台转换层判，④ 面按渠道（有时按模型）判；用 schema 与 prompt 冲突的用例验证（04 §2）。
151. **同一台中转站换个渠道的同名模型，账单变贵、输出上限失效。**
    原因：anti 渠道每个请求多约 30 token 注入（「Say OK.」报 39 输入，其他渠道 9–10），没有缓存字段、每次按全价输入；`max_tokens` ① 面无视、④ 面生效【实测 2026-09-23】。
    对策：usage 可信度、缓存、输出上限都按渠道记；用最短的「Say OK.」对照各渠道的输入 token 就能看出注入（06 §1）。
152. **为了给中转站的某个渠道关能力，代码里写了 `/\[CC量\]/` 这样的正则。**
    原因：`[CC量]` `[anti量]` `[正向AWSb量1]` 是这台站主起的缩写，换一台中转站同一个渠道叫别的名字——正则漏点名，也可能误中别家的同名缩写【参考实现的决定 2026-09-23】。
    对策：代码里的名单只收上游产品名认得出的渠道（kiro、bedrock 类）；其余渠道做成作者声明的数据（给模型行选一个渠道画像），id 正则只当默认建议（01 §9.2 第 7 条）——参考实现已这样做（01 §9.2「上游做成作者声明的数据」，坑 153–158 是做完之后踩的）。

## U. 中转站上游做成数据之后：一个事实被第二处代码重推（详见 01 §9.2「上游做成作者声明的数据」）

来源：simple-ai-writer PR #687 / #688，逐片 review、三轮整体 review 与修正 PR 的五轮 review（2026-09-23），`docs/api/capability-gating-plan.md` §8.11。
上游 = 中转站背后的后端（Kiro / CC / anti / Bedrock / 官方），由「模型手选 → 渠道前缀表 → id 里的产品名」解析。这一组的共同成因：
**解析只该发生在一处，却有第二处代码自己又推了一遍**——两处答案一不同，就是资格与请求、提示与请求、合并前与合并后说两句话，而且都不报错。

153. **子代理页说这个模型能读 PDF / 能联网，委派后请求里却没有（或反过来）。**
    原因：资格判断（`readsPdf`、`serverToolsSent`）只看模型 id 推断上游，不看渠道上的前缀表；请求经 `connOptions()` 走了表。
    `[CC量]claude-opus-5` 在 ④ 面：表说 CC（能读 PDF），只看 id 则「无上游」→ 中转站 ④ 面缺省不读——子代理页把它挡在门外，请求本来能发【实现 2026-09-23，review 找出】。
    对策：每个问能力的地方都带上渠道（含前缀表）并经同一个解析函数；为「读取方跟着表走、手选压过表」写单测，别只测适配器。
154. **某个界面发出的请求不按作者配的上游裁决，还是按 id 猜。**
    原因：该调用点手拼请求参数（参考实现的「生成提示词」按钮），没展开 `connOptions()`，上游字段缺省——适配器于是退回按 id 推断，作者的前缀表与手选全被跳过【实现 2026-09-23】。
    对策：连接参数只在一处摊平（01 §7）；「缺省时按 id 推断」只留给 live 探测、端点探测这类手搭请求。一致性测试覆盖不到调用点，用源码扫描或 review 清单查「手拼 options」。
155. **合并两行渠道后，作者专门给某个模型选的上游没了，退回成从 id 猜的那个。**
    原因：合并逻辑把「从 id 推断出的上游」当成「合并前已有上游」，同 id 折叠时它压过被吸收行的手选：`kiro-claude-opus-4-6` 被吸收行手选 CC，合并后退回 Kiro，④ 面 PDF 由发变不发。
    并表说法不同时，这个推断还被写成模型的手选，抽屉显示「手选」【实现 2026-09-23，整体 review 找出】。
    对策：推断不是谁的设置——不参与优先级，也永不写成手选；合并前后 id 不变，推断会自己重新算出来。只有作者给的（手选、前缀表）才需要保持或钉住。
156. **合并后，作者给某个模型手选的上游被保留行表里的一行前缀静默盖掉。**
    原因：同 id 折叠时先看保留行的前缀表、后看被吸收行的手选。保留行表 `[x]` → anti，被吸收行 `[x]claude-opus-4-6` 手选 CC，合并后解析成 anti，
    ① 面 PDF 由发变不发（anti 的 ① PDF 是 ✗）【实现 2026-09-23，修正 PR 第 1 轮 review 找出】。
    对策：优先级处处一致——**针对这个 id 的选择 > 覆盖一批 id 的表行 > 推断**，合并也不例外：保留行手选 → 被吸收行手选 → 本行前缀表（冲突时钉住）→ 并表。
157. **提示让作者去做一件做不成、或已经做了的事。**
    原因：提示自己推理「为什么不行、该怎么办」，没问请求用的那个裁决。三种表现【实现 2026-09-23】：
    - 模型已勾 PDF、只是当前线路传不了，提示说「未声明支持 PDF，去勾上」；
    - 建议「换到能传 PDF 的线路」，可中转站上有 PDF 拼法的线路仍会被上游丢文件——Kiro 模型从 ④ 换到 ① 只换来「上游丢 PDF」；
    - 同一模型在 ① 上被劝换模型、在 ④ 上被劝换线路，建议随当前线路变。
    对策：
    - 「不行」按原因分说法：未声明 / 上游丢 / 线路传不了。
    - 「换到哪」逐条线路问同一个裁决（`readsPdf(model, 那条线路)`），有能传的就点名，没有就只建议换模型；不论原因，这一步都做。
    - 未实测的线路按能力表缺省算能传，与请求一致；文档说不支持、却没实测的，宁可留一处写明的出入，也不凭文档写 `false`。
158. **作者选了「不按上游」，模型还是被当成 Kiro 裁决。**
    原因：`"none"` 被存成空值，或读取时当成「没选」——解析继续往下走到 id 推断，`[特价kiro量]claude-opus-5` 又变回 Kiro【实现：参考实现从设计起就防这一条】。
    对策：`"none"` 是一个**解析结果**，不是空缺：存储三态（没选 / 选了某上游 / 不按上游），`connOptions()` 解析后恒有值（某上游或 `"none"`），
    只有字段缺省才推断。一致性测试放一个「id 含 kiro、却选了 `none`」的用例，验证矩阵与适配器都回到平台默认。

## V. 同一台中转站、同一个 GPT、账号池与网关两类上游（详见 01 §9.2「同一个 GPT，两类上游」「上游画像扩到 GPT」、02 §7.1、03 §7.4、04 §5.1、05 §5「中转站上的 GPT」、06 §1 / §2 / §4.1 / §5 / §8）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十七个样本（一台 New API，`gpt-5.6-sol` 挂在 `[特价Pro]` / `[Plus]` / `[Pro]` 三个 ChatGPT 账号档与 `[Azure]` 网关下，网关用 terra 顶替；
② ① 两族约 560 次 curl + 真实 ② 适配器四档各一轮）、`docs/api/capability-gating-plan.md` §8.12。账号池 = Codex 后端的反代；网关 = 参数面最像官方、却挂着护栏的正向线路。

159. **写作应用在某个档位上时不时拒写小说，说自己「只能做 OpenAI 相关的工作」。**
    原因：网关类上游只要看见 `instructions` 键（**哪怕是空串**）就在后面追加约 1.2K token 的「System integrity addendum」，明文让模型拒绝 fiction、novels、poems、role-play；
    中转站在前面插了一段反制，大体压得住但不是每次——鬼故事 6 次拒 2 次，一道数学题、一次结构化输出的字段里也出现过。200、没有 `refusal`，只是答案不对【实测 2026-09-24】。
    判据：回显的 `instructions` 比发出去的长；「Say OK.」带 `instructions` 报 1,209 输入、不带报 9。
    对策：这条线的能力表判 `instructionsField: false`，系统提示作为 `input` 开头的 `{role:"developer"}` 消息发、不发 `instructions` 键——实测护栏消失、创作题照写（01 §9.2、02 §7.1 规则 2）。
160. **结构化输出在一个档位上「偶尔」不按 schema，另两个档位好好的，而且省略 `strict` 也没用。**
    原因：`[Pro]` 账号档把 ② `text.format`（省略 `strict` 与显式 `strict:true` 各 4/4）与 ① `response_format` 都整个丢掉，回显 `{type:"text"}`；
    提示语仍要求 JSON，所以回的还是合法 JSON，只是不受 schema 约束——同一种上游的 `[Plus]` / `[特价Pro]` 都执行【实测 2026-09-24】。坑 63 的「显式 `strict` 才丢」是另一台、另一时间的 `[Pro]`。
    对策：用 schema 与 prompt 冲突的用例验（04 §2）；同一种上游结果不一，不写能力格，在模型说明里告知；运行时可比对终止响应回显的 `text.format`（06 §4.1）。
161. **「关闭思考」选了，账单上照样有推理 token，回答也照样慢。**
    原因：GPT 在这台中转站上 ② `reasoning.effort:"none"` 四个上游都被改成 `medium`（回显看得见）；① `reasoning_effort:"none"` 只在网关上真关，账号池照样推理【实测 2026-09-24】。
    对策：回显比对报告改写（06 §4.1），作者说明写「这个上游关不掉思考」；思考能力按面记（同一上游 ① ② 可以不同，03 §7.4）。
162. **调了温度，输出风格毫无变化；换一个档位，同一个温度让每个请求都 500。**
    原因：账号池上游把 ② `temperature:0.5` 静默改成 `1.0`（回显 `1.0`）；网关上游 `temperature ≠ 1` 就 500 `Upstream gateway error`（6/6，`1` 则 200）。① 面两者都 200、没有回显，分不出生效没有【实测 2026-09-24】。
    对策：两类上游的 ② `temperature` 都判「不发」；① 不写格子。500 那种会响，但整条失败——对中转站默认发温度的实现在这个上游上一个请求都跑不通（06 §2）。
163. **开了联网搜索，模型却说「I can't perform a live web search」。**
    原因：网关上游把 ② `web_search` 静默丢掉，响应里没有 `web_search_call`；同一台、同一个模型 id 的账号池上游真搜（6–10 s、带 `url_citation`）【实测 2026-09-24】。
    对策：`web_search` 能力按上游声明（账号池 ✓、网关 ✗）；「搜没搜」只看 `web_search_call` 条目（05 §5）。
164. **① Chat 面开了 `web_search_options`，不报错，答案却显然没联网。**
    原因：这台中转站把 GPT 的 ① 翻成 ② 再发，翻译层不转 `web_search_options`——四个上游全部静默忽略【实测 2026-09-24】。
    对策：GPT 的联网只走 ② `web_search`；中转站 ① 面不给 GPT 声明搜索能力（05 §5「中转站上的 GPT」）。
165. **输入 token 忽多忽少：同一个请求有时 9、有时 4.4K、偶尔 17K，带了 system 也一样。**
    原因：同一档位背后是多个 ChatGPT 账号，注入与否、注入多少随落到的账号变（`[特价Pro]` 见过 0 / 11 / 296 / 4.4K / 17K）；① 面带 system 消息也照样注入（`[特价Pro]` 4,397、`[Plus]` 4,395；`[Pro]` 只在带具名 `tool_choice` 时注入 4,434）【实测 2026-09-24】。
    对策：GPT 走 ② 并发 `instructions`（三档都 19，不注入）；需要核实时读 `usage.attribution.request_fields.instructions.input_tokens`（06 §1）；注入与计费类结论同一请求跑 3 次以上（06 §8 第 11 条）。
166. **按模型列表的 `supported_endpoint_types` 给模型开了 ④ / ③ 线路，一用就 4xx；目录里列着的模型一请求就 503。**
    原因：New API 的目录对 GPT 账号档声明 `anthropic` / `gemini`，这把 key 的分组却不许（`This group does not allow Anthropic Messages requests`）；
    目录里的 `[Azure]` / `[官key]` sol 当时没有线路，回 503 `No available channel for model … under group …`【实测 2026-09-24】。
    对策：线路以作者选的为准，不按目录自动开；「No available channel」报成「这一档当前没有线路」，不报成模型名写错（06 §5）。
    【2026-09-26 补】反方向也有：OrcaRouter 的 `gpt-6-luna` / `-sol` 只声明 `openai`，打 ② 照样 200——这个字段多了少了都见过（01 §9.5）。
167. **URL 图片在一个档位上整条 500 `count_token_failed`，在另一个档位上是 200 + 空答。**
    原因：中转站为了计 token **自己先下载一遍** URL 图片，图放在拒爬虫的主机上时下载失败、整条 500（请求没到上游）；别的上游自己下载失败则回 400 `Error while downloading file`，或流里一个 `error` 事件后接空答【实测 2026-09-24】。
    对策：图片一律内联 base64 / data URL；流内 `error` + 空答当失败（06 §2）。
168. **能力表里给一个上游写了 `temperature: false`，矩阵说不发，请求里照样有；模型抽屉的摘要也照列。**
    原因：问能力的几个地方里有的没带上游——② 适配器的温度根本不查表，verbosity、模型摘要、模型抽屉的温度与 verbosity 查表时不带上游。以前没有哪个上游在这些格子上写过 `false`，所以一直看不出来【实现 2026-09-24，review 找出】。
    对策：每个问能力的地方都经同一个 `capabilityModelOf`（与坑 153、154 同一条）；一致性测试的上游夹具由上游清单生成、同时带 Claude 与 GPT 的 id，新上游、新格子当天就被覆盖。
169. **为了躲网关的护栏把 `instructions` 全局换成 developer 消息，账号池档位的输入 token 每请求涨 4.4K。**
    原因：两类上游在同一个开关上方向相反——账号池找不到 `instructions` 就注入 Codex 提示（坑 62），网关看见 `instructions` 就挂护栏（坑 159）【实测 2026-09-24】。
    对策：「这条线收不收 `instructions`」做成能力表里按上游裁决的一格（`instructionsField`，协议缺省 yes），不做全局开关，也不做绕开能力表的特判字段（01 §9.2「上游画像扩到 GPT」）。

## W. 一台网关背后几种后端：回包原样、请求被重新序列化（详见 01 §9.5、03 §2 / §3 / §5、04 §2、05 §3 / §5、06 §1 / §2 / §8）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十八个样本、`docs/api/orcarouter-probe-plan.md` §7（OrcaRouter 付费 key，约 120 次 curl + 真实四族适配器 28 条 live 用例，
修复前 23 条过、修复后 28 条全过）。这台网关的 ④ 是 Anthropic 原样、③ 是 Vertex AI 原样，① 与 ② 默认线路是一层 OpenRouter 形态的翻译，而**四个面的请求都被重新序列化**——
所以下面凡是「会不会 400」的原因都只对这台网关成立，回包形状可以当官方记。

170. **Gemini 选「关闭思考」，每个请求都 400 `Thinking level MINIMAL is not supported for this model.`**
    原因：「关闭」映射成了 `thinkingLevel:"MINIMAL"`；3.8 Flash 不收（文档里 3.1 Pro 也没有），缺这一档时是 400 而不是降级。枚举由上游校验，报文是 Vertex 原文【实测 2026-09-26】。
    对策：「关闭 / 尽量少想」映射到每个型号都收的最低档 `LOW`——多想几百 token 是便宜的一边，报错是最坏的一边；不需要为此按型号探测（03 §2）。
171. **Gemini 发 `thinkingBudget: 0` 想关掉思考，账单上照样有几百思考 token。**
    原因：3.8 Flash 仍接受旧字段 `thinkingBudget`，但 `0` 照想（312 token）；经网关测得，可能是重新序列化时把 `0` 当空值丢了【实测 2026-09-26】。
    对策：不拿 budget 0 代替缺席的 `minimal`；只发一代字段（Gemini 3 发 `thinkingLevel`），「关不掉」写进作者说明（03 §2）。
172. **Gemini 的流式工具调用，第二轮必 400 `required oneof field 'data' must have one initialized field`；非流式好好的。**
    原因：流以一个光秃秃的 `{text:""}` part 收尾，「整组原样回灌 parts」把它也带了回去；经 OrcaRouter（Vertex）400，而带签名的 `{text:"", thoughtSignature}` 200
    ——可能是网关把空串当空值丢成了 `{}`，未必是 Vertex 本身【实测 2026-09-26】。只测非流式或只测单轮都发现不了。
    对策：回灌时剔除既无文本、也无签名 / 调用 / 其他数据的空 part，带签名的保留；**读已存的历史时也过滤**，否则修复前存下的会话照样 400（05 §3）。
173. **Gemini 工具轮回灌后 HTTP 400 `Function call is missing a thought_signature in functionCall parts`，而错误处理只认 200 + `MISSING_THOUGHT_SIGNATURE`。**
    原因：3.8 Flash（Vertex）对缺签名的 `functionCall` 直接 400，不是文档说的 finishReason 形态；并行调用时签名只挂在**第一个** `functionCall` part 上，流式时落在最后一块的 `{text:"", thoughtSignature}` 上【实测 2026-09-26，经网关】。
    对策：整组原样回灌（空 part 例外，坑 172）；两种形态都报成「我方丢了签名」，不让作者去自己的内容里找原因（03 §5、06 §2 第 4 条）。
174. **经网关实测「发 X 不会 400」，换到官方端点就 400；或者按「乱写 effort 200 = 反代」把一个原样后端判成了反代。**
    原因：网关把 body 解析后重新序列化——④ 顶层未知字段、`thinking.type:"bogus"`、`output_config.effort:"bogus"` 都 200（官方对多余字段 400）；③ 未知字段 200、枚举却由上游校验；
    ② 默认线路非法 effort 回网关自己的 `upstream_rejected_request`；而回包是上游原样，很容易把整台网关当透传【实测 2026-09-26】。
    对策：按面用透传证据判后端（01 §9.5 的清单、漏出的上游响应头）；回包形状记成官方事实，「会不会 400」只记成网关注记；06 §8 第 10 条的非法参数分类法先过第 12 条。
175. **同一个 `/v1/responses`：前一个请求 id 是 `gen-…`、条目 id 是 `msg_tmp_…` / `fc_tmp_…`、带 `usage.cost`；开了 `store:true`（或要了搜索来源）之后变成 `resp_…`、多出 `billing`、花费字段没了。**
    原因：网关按请求字段分流：默认走 OpenRouter 形态的翻译层，`store:true` 或 `include` 含 `web_search_call.action.sources` 才换到 OpenAI 原样；`web_search` 工具、`reasoning.encrypted_content`、`text.verbosity` 都不触发【实测 2026-09-26】。
    两条线的 id、事件、花费字段、`summary` 回显都不同，回灌规则在两条线上都测不出来（网关多半改写了 `input`）。
    对策：不按 id 前缀或花费字段的有无推断条目类型与能力；花费「有就读、没有就按表算」；功能开关会改 `include` / `store` 的，两条线都要测（01 §9.5）。
176. **调了 Gemini 的 `:countTokens` 想估长度，账单上多出一笔生成费，返回的是一段关于「数 token」的作文。**
    原因：OrcaRouter 把 `:countTokens` 当成 `generateContent` 执行并计费（$0.0028）；④ `/v1/messages/count_tokens` 则 301 到官网首页【实测 2026-09-26】。
    对策：经中转的计数端点先确认没被当生成执行再用，否则只用本地估算（01 §6）；这台网关上不调它（01 §9.5）。
177. **按 `error.type` 分类的错误处理在中转站上全部落空：`type` 读到 `"<nil>"`，报文里的字段路径是 `***.***.content.0`。**
    原因：网关把上游错误改写成 OpenAI 形——③ `type:"invalid_argument"`、`code:400`，路径与 URL 被遮；④ `type:"<nil>"`（Go 的空值，New API 系指纹）；上游 5xx 变 `api_error` 固定文案；
    文档说的 `claude_error` / `gemini_error` 一次都没出现。回包是原样的面，错误也不一定原样【实测 2026-09-26】。
    对策：分类只靠 HTTP 状态 + 报文关键字；降级正则匹配参数名，不匹配被遮的路径（06 §2）。
178. **Gemini 开了联网（`googleSearch`），按 token 估的成本比账单低得多。**
    原因：检索另计，token 部分只是零头【实测 2026-09-26，读网关的 `usageMetadata.costUsd`】。原写「一次 $0.028」是按请求记的；
    同日再补测按查询条数核对，**约 $0.014 一条**，一次回答搜几条由模型定（坑 190）。
    对策：服务端工具的次数与按次费用单列；有上游报价就用报价（06 §1）。
179. **Claude 开了 `web_search`，一个 `cache_control` 都没打，用量里却出现几千 `cache_creation_input_tokens`，按缓存写价计了费。**
    原因：搜索结果被服务端自动写缓存（一次 2,834）；`usage.server_tool_use.web_search_requests` 另报次数【实测 2026-09-26，Sonnet 5，回包原样】。
    对策：`cache_creation` 不当「我方打了断点」的判据，也别当缓存逻辑的 bug 去查；三桶照样相加（06 §1、05 §5）。

## X. Anthropic 的结构化输出只有严格档（详见 04 §2「④ 的 schema 模式」、03 §2）

180. **给 Claude 的结构化任务照搬三档降级：schema 被拒后「降到 json_object」，界面写着 JSON 模式，请求里却什么都没有。**
    原因：④ 只有 `output_config.format`（严格档），没有「任意 JSON 对象」开关；阶梯里的中间档在这一族不存在。降级记成 json_object 封顶后，发送端正确地退成了 cue，显示端却照读那个封顶【2026-09-26 review 发现】。
    对策：按族给出可用档位（④ 只有 schema / off），解析与显示读同一个「该族有没有这一档」的答案；被拒后显示「关闭」（04 §2）。
181. **给 Claude 打开结构化输出后，思考强度的设置悄悄失效（或者反过来，schema 没发出去）。**
    原因：`output_config.effort` 与 `output_config.format` 在同一个对象里；两段代码各自产出 `{output_config: …}` 再平铺合并，后写的整块盖掉先写的。
    对策：合并进同一个对象；测试钉住「effort 与 format 同时在」（04 §2）。
182. **同一份输出 schema，OpenAI / Gemini 都好好的，发给官方 Claude 就 400；经中转站测却一直 200。**
    原因：④ 不支持数值上下界、长度、`pattern`、`minItems > 1`、递归，对象必须 `additionalProperties:false`；官方 SDK 在发送前剥掉，手写请求不会。中转站重新序列化请求，这些在网关上都是 200【实测 2026-09-26，只对网关成立】，所以经中转测不出来。
    对策：strictify 之后按 ④ 的支持表再剪一遍关键字；不拿中转站的 200 当官方接受（04 §2、坑 174）。
183. **Claude 的结构化输出按型号名单自动开，官方的 `claude-opus-4-5-20251101` 开了，中转站的 `anthropic/claude-opus-4.5` 没开。**
    原因：官方 id 用连字符，中转站常用点号；按前缀匹配的名单只写一种拼法，另一种静默不命中——不报错，只是一直停在 cue。
    对策：名单两种拼法都列（剥掉厂商前缀后再匹配），并用中转站的真实 id 写一条测试（04 §2）。
184. **Opus 5.5 / Fable 5.1 的「关闭思考」请求整条 400 `requires adaptive thinking`，Sonnet 5 同样的请求却没事。**
    原因：新一代部分型号不收 `thinking:{type:"disabled"}`【实测 2026-09-26】；「关」在 ④ 上不是全族通用的值。
    对策：④ 的「关闭」发 `adaptive` + 最低 `effort`（官方也这样建议），不发 `disabled`（03 §2）。

## Y. 网关报价进账、Gemini 内置工具、执行日志 id（详见 06 §1「第四种口径」、05 §5「③ Gemini 的内置工具」「响应流的防御读取」、01 §9.5、02 §1 表后）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十八个样本「再补测」A–D（OrcaRouter，流式、按应用真实会发的形态，脚本约 25 次 + live 用例）、
`docs/api/orcarouter-probe-plan.md` §8、`docs/feature/billing/01-fee-groups.md`「上游报价」，以及那一轮的逐提交与整体 review。

185. **一个贴着「受信网关」标签、地址却指向别的中转的渠道，用量按它自己回的 `usage.cost` 定了账。**
    原因：信任只看了平台标签。标签是作者贴的，选了某平台再改地址，标签不跟着变；而 OpenRouter 形态的翻译层在 ① 上本来就回 `usage.cost`——
    没测过的中转报的数是不是它实扣的，没人知道，报价却压过整张价格表【实现 2026-09-26，review 找出】。
    对策：两道门——平台声明过「报价 = 实扣」（与平台账单接口逐笔对过），**且**从请求地址推断出的平台与标签一致，才发请求头、才收数（06 §1）。
186. **接了网关报价，④ 与 ③ 的用量却一直按价格表算（没配价格的就是 $0），回包里找不到花费字段。**
    原因：OrcaRouter 的 ④③ 只在请求带 `X-OrcaRouter-Include-Cost: true` 时报；④ 报在 `message_delta.usage.cost_usd`，`message_start` 的快照里没有；
    ③ 在末块 `usageMetadata.costUsd`。先前的非流式观察没交代这个头，应用只发流式【实测 2026-09-26】。① ② 默认线路不带头也报（`usage.cost`），② 原样线路永远不报。
    对策：请求头从换算报价的同一个模块出，四个适配器都带；④ 在 `message_delta` 读；实测时按应用真实的流式形态测（01 §9.5、06 §8 第 7 条）。
187. **agent 跑了五轮，只有三轮报了价，用量行按三轮的和记，另外两轮成了免费。**
    原因：多次请求合成一行时（agent 多轮、④ `pause_turn` 续接、分段摘要）把「没报」当 0 加进去——报价又压过价格表，没报的那几轮就白用了。
    对策：全报才加，缺一次整行为空，回落到价格表按**全部** token 算；累加器区分「还没有任何一次」（接过第一次的值）与「有一次没报」（此后恒为空）（06 §1）。
188. **草稿卡片上显示的花费与用量页记的不是一个数。**
    原因：记账接了上游报价，显示路径仍只按价格表算（或反过来）；两处各有一份算式。
    对策：显示与记账都经唯一的 `costOf()`、都接报价（06 §1）。
189. **重构后某个调用点漏传了报价，CI 全绿，没配价格的网关模型从此静默记 $0。**
    原因：漏传不会出错，那一行只是按表算。防它的源码扫描护栏只看调用括号里的文本：参数对象先在别处构造、用展开写法、导入时换了别名，三种写法都看不见——
    变异一处（先组 `row` 再传、不带报价）护栏照样绿，名单里的一条豁免也从来没被用到过【实现 2026-09-26，第 2 轮整体 review 做变异发现】。
    对策：让类型来拦——写入口的参数把报价做成必填键（`reportedCost: number | null`，没有就显式写 `null` 并注明理由），显示算式的同名参数不给默认值；
    三种写法都编译不过，扫描护栏删掉。**源码扫描护栏看不清时应当报错而不是跳过**；能交给类型的约束优先交给类型（06 §1）。
190. **Gemini 开了联网，一个问题花了 $0.08，而平时一次搜索才一两美分。**
    原因：`googleSearch` 按**查询条数**计费（约 $0.014 一条），一次回答搜几条由模型定——带函数工具 + 响应 schema 的一次搜了 6 条、$0.084；
    这个协议没有像 ④ `max_uses` 那样的上限字段可发【实测 2026-09-26，经 OrcaRouter（Vertex）】。
    对策：设置说明写「按条计费、条数由模型定、无法设上限」；执行日志逐条显示搜索词（`groundingMetadata.webSearchQueries`）；有上游报价就用报价（05 §5、06 §1）。
191. **Gemini 用了读网页或代码执行，记下的输入 token 比账单少一截。**
    原因：内置工具回填给模型的 token 在 `usageMetadata.toolUsePromptTokenCount`，**不在** `promptTokenCount` 里（20 + 65 + 77 = total 162）【实测 2026-09-26】；
    只读 `promptTokenCount` 就漏掉它——有上游报价时钱是对的，token 数仍偏少。
    对策：`inputTokens = promptTokenCount + toolUsePromptTokenCount`，与 `thoughtsTokenCount` 计进输出同理（06 §1 第 2 条）。
192. **执行日志里第 1 轮读过的网址那一行不见了（或跑到第 3 轮的状态）；三份草稿搜了同一组词，日志只剩一行。**
    原因：Gemini 的内置工具事件没有上游生成的唯一 id，读取器用内容拼 id（`url:<网址>`、`search:<搜索词>`、每个请求都从 1 数起的代码序号）；
    执行日志按 id 原地替换、比较时不带轮次，而一份日志装着好几个请求（agent 多轮、同一上下文并发的多份草稿）。按次计费的工具于是少记，
    作者唯一能看到用了几次的地方数错了【实现 2026-09-26，逐提交 review 找出】。
    对策：每个读取器生成请求级前缀，id = 前缀 + 内容键；本请求内去重仍按内容键；上游自带的序号类 id（未核实跨请求唯一）也加前缀；测试钉住两个读取器读同一块 id 不同（05 §5）。
193. **搜索结果分几块到时，日志里的搜索行只有空结果；或者搜索词逐块累加时多出一行、同一次搜索算两次。**
    原因：搜索行「每个阶段只报一次」、id 由搜索词拼成——先到的不完整结果把后来的命中挡掉，搜索词一变 id 就变【实现 2026-09-26，review 找出；
    实测 grounding 只在末块出现，所以今天碰不到，但读取端不该依赖】。
    对策：一个请求一个固定的搜索 id（前缀 + `search`），内容变了就用同一个 id 重发，靠日志的原地替换更新；去重比较内容签名，不比「报过没有」（05 §5）。
194. **只开了 Gemini 的读网页（`urlContext`），执行日志却记了一次搜索。**
    原因：读网页的回答末块也带 `groundingMetadata.groundingChunks`（给出真实 `uri` 与页面标题），但**没有** `webSearchQueries`；把「有 groundingChunks」
    当成「搜过」就多记一次按条计费的搜索【实测 2026-09-26】。另外，搜索的 `groundingChunks[].web.uri` 是 `vertexaisearch` 跳转链接、`title` 是域名，不是原站与页面标题。
    对策：「搜过」只认 `webSearchQueries`；读网页的回报在**首块**的 `urlContextMetadata.urlMetadata`（05 §5）。
195. **开过代码执行的 Gemini 会话越来越接近上下文上限，估算却没怎么涨。**
    原因：`executableCode` / `codeExecutionResult`（以及可能带回的 `inlineData` 图表）随整组 model parts 原样回传，每轮都在请求里；
    它们和思考签名走同一套回传机制，上下文估算与历史裁剪都不计它们【实现 simple-ai-writer，写成已知限制】。回传本身没问题：
    请求里撤掉 `codeExecution` 甚至撤掉全部工具也 200【实测 2026-09-26】，所以不必改写成文本。
    对策：估算把回传的 model parts 按实际字节计入；大输出 / 图表的代价写进说明（05 §5）。
196. **按默认建好网关渠道，保存前删掉一条暂时不用的线路，钉在那条线路上的起步模型一调就报「线路不存在」。**
    原因：起步模型各钉在最能体现它的面（④ 的 Claude、③ 的 Gemini、② 的 GPT），建渠道时直接照抄钉的线路，没看这条线路还在不在【实现 2026-09-26，review 找出】。
    对策：钉之前过一个纯函数——线路还在才钉，否则不钉、跟主线路走（`pinnableRoute`）。事后编辑渠道再删线路，由解析层明确报 routeNotFound（会响），
    是否自动回退是取舍，参考实现选了不回退并写进文档（01 §9.5）。
197. **一页 PDF 的请求比按文字估的贵：Gemini 记了 520 输入 token，Claude 没打 `cache_control` 却记了 1,630 缓存写入。**
    原因：③ 把 PDF 页**按图像计**（一页 520 token），不按抽出的文字；④ Sonnet 5 读 PDF 时服务端自己写了缓存（Opus 5.5 同样的请求没有，原因未明）【实测 2026-09-26，经 OrcaRouter，回包原样】。
    对策：PDF 按页估成本，不按文字长度；`cache_creation` 不当「我方打了断点」的判据，三桶照样相加（坑 179 同一种现象；02 §1 表后）。

## Z. ④ 开关型思考的温度、「关闭」只是最低档时的思考回退（详见 03 §2.1、§3.4、06 §8 第 13 条）

来源：simple-ai-writer `docs/api/landscape.md` §7 第四、第十二个样本「B6 补测」与第十八个样本「思考回退补测」、`docs/issues/anthropic-temperature-thinking-off.md`、
`docs/api/capability-resolution-lld.md` §9.11–§9.12（2026-09-28，火山方舟 Coding Plan、MiniMax 国内站、OrcaRouter 上的 Claude Sonnet 5 与 Gemini 3.8 Flash）。

198. **火山方舟 ④ 关了思考、温度填 0 求稳，20 次挑选照样分散。**
    原因：这条线路关思考时听温度，但把 `0` 当成「未设」落回缺省——`0` 四轮 9–13/20，与不发（8–13/20）分不开，`0.01` 才收敛到 19–20/20；① 面上 `0` 是生效的【实测 2026-09-28，`doubao-seed-2.0-mini`】。
    对策：这一类目的温度栏下说明「这条线路把 0 也当作没填，要最稳填 0.01」，填 0 不挂「确定性」标签；不在适配器里把 0 改写成极小正数——那是改写作者的值（03 §3.4）。
199. **把 ④「在想就不发温度」改成「线上没在想就发」，MiniMax 关思考时开始发温度，界面多出一个改了毫无效果的框。**
    原因：MiniMax-M3 的 ④ 面收下温度、不理会（`0.01` 与 `1`、与不发分不开，开关思考都一样；① 面也看不出）【实测 2026-09-28】；同一拼法的火山方舟却听。
    对策：「关思考时听温度」是思考类目上的声明，只挂在听的那个类目上，不按线上思考状态一刀切（03 §3.4）。
200. **「关思考时听温度」写进了平台格，请求里照样没有温度；中转站上手选了同一类目的行也拿不到。**
    原因：能力裁决里请求条件（在不在想）先于平台格求值，条件一触发就返回，格子轮不到；要让格子盖过条件，得给求值顺序加特例。平台格也只覆盖那一个平台。
    对策：事实挂在思考类目上，发送端与界面问同一个「听不听温度」函数（03 §3.4；裁决次序见 01 §9.2）。
201. **④ 思考开着时带 `temperature: 0.3`，指望它像官方那样 400、再学着不发——结果 200，什么都没学到，温度也没生效。**
    原因：火山方舟与 MiniMax 的 ④ 面开思考时都 200 而不收敛（官方是 400）【实测 2026-09-28】。
    对策：在想就不发；理由写成「发了没人听」而不是「会 400」，不指望按 400 学降级兜这类字段（03 §3.4、06 §9）。
202. **测「温度生不生效」用开放题数不同句子，结论「分不出」；换一道只有几个答案的题，又在某个模型上得出「缺省就很稳、温度无所谓」。**
    原因：开放题每句都不一样，温度 0 下句子开头趋同、不同句子个数照样是 5；缺省已把那道题收敛的模型（MiniMax-M3 不发温度就 19–20/20 答同一种水果）在那道题上什么都说明不了。
    对策：有限答案题 × 每档 20 次，至少两道、以缺省最分散的那道为准，`0` 单列一档（06 §8 第 13 条）。
203. **agent 思考超限被中止后回退「关思考」，重发的那次和被中止的那次想得一样多。**
    原因：③ 的「关闭」是 `thinkingLevel:"LOW"`、④ 是 `effort:"low"`——只是最低档；Gemini 3.8 Flash 不设档位时本来就在最低档附近（输出 token 中位数不设 1,980、「关闭」1,977）【实测 2026-09-28，经 OrcaRouter】。
    对策：类目声明 `offSpelling`（真关 / 最低档）；最低档类目既发 off 又带「不要展开思考，直接作答」一句，真关的只发 off（03 §2.1）。
204. **回退改成只加「别想了」提示、保留作者的档位，偶尔 1–3 个输出 token 直接报数——Gemini 那几次全答错。**
    原因：提示的效果是两极的：多数照常思考只是短些，少数整段跳过【实测 2026-09-28：Gemini 高 + 提示 3/5 答对，跳过思考的两次都错；Claude 跳过的几次都对】。
    对策：off 与提示一起发（两家都最省：1,396 / 1,300 输出 token，4/5、5/5 答对），不单用提示（03 §2.1）。

## AA. 视频输入 `video_url` 按平台（详见 02 §1 表后「视频输入」）

来源：simple-ai-writer `docs/api/landscape.md` §7 第十九个样本、`docs/issues/video-capability-per-platform.md`（2026-09-28，六个端点各发一段 4 秒红转蓝片段）。

205. **经网关给 Gemini 发了一段视频，200、回答头头是道，其实视频根本没到。**
    原因：OrcaRouter 的 ① 层静默丢 `video_url`：输入 token 与不带片段逐个相同（25 → 25），三次回答三种颜色都错；Gemini 本身读视频，丢在网关的翻译层【实测 2026-09-28】。
    对策：视频输入按平台点名放行，这个面判不收；验证用猜不出的片段，比带与不带片段的输入 token（02 §1）。
206. **① 族平台一律放行视频输入：DeepSeek 422 `unknown variant video_url`、xAI 400 `Empty content block`、网关上的 GPT 400。**
    原因：`video_url` 不是 Chat Completions 规范里的片段类型，是千问一族兼容端的扩展；按族放行 = 拿协议族回答平台的问题【实测 2026-09-28】。
    对策：平台格——实测收的点名（百炼、火山方舟 Coding Plan、智谱），实测不收的写 `false`，没测过的不发；中转站 / 自定义渠道判未知。旧行上的视频声明保留，界面说「已声明，不发送」（02 §1）。
207. **视频夹具在百炼上 400 `Invalid video file`，于是得出「这个模型不读视频」。**
    原因：百炼对片段本身挑剔：320×240 / 10 fps 的纯色片段被拒，改成 640×480、或加一层噪点就收【实测 2026-09-28】。
    对策：夹具先在已知收视频的对照端点上过一遍；纯色测试片段用 640×480 以上（02 §1）。
208. **给火山方舟发 `fps: 1` 想省视频 token，账单一点没变。**
    原因：4 秒片段上 `fps` 两种拼法（片段旁边 / `video_url.fps`）、取 1 与 0.2，输入 token 都与不带时相同；片段可能在最少帧数之下，是否认 `fps` 未定【实测 2026-09-28】。百炼同一招 1,241 → 641。
    对策：`fps` 生效与否按平台单独记，不从百炼推；没定论前不给这个平台写「`fps` 生效」（02 §1）。

## AB. 按 400 学降级：一个执行器、学到的上限持久化（详见 06 §9）

来源：simple-ai-writer `docs/api/capability-resolution-lld.md` §3.7、§9.13 与 HLD §6 D3 改判、`provider-layering.md` §7 第一条（2026-09-28 落地，含逐提交与整体 review、变异测试）。

209. **一个已被降成 `auto` 的请求撞上点名 `tool_choice` 的 400，执行器学一次、原样重发一次、再失败。**
    原因：分类比对的是「请求了强制」，而适配器早已按类目 / 格发了 `auto`——这个 400 不是强制的错【实现 2026-09-28】。
    对策：比对请求计划**实际发出**的强制与档位（06 §9.1）。
210. **两个并行请求撞同一个 400：一个降级重试成功，另一个直接报错。**
    原因：重试条件写成「这次调用严格降低了上限才许重试」；先学到的那个降了上限，后到的发现不是自己降的就抛错。这条对终止性其实是空的——变异测试去掉它，循环照样终止【实现 2026-09-28】。
    对策：学到即重试。终止性由分类表保证：只在请求用了该事实且存在更低一档时才分类，下一轮计划受上限约束，每次重试发出的严格更少，至多三次（06 §9.2）。
211. **结构化任务在本地模型上走 JSON 路径时报 chat 模板错误，云端一切正常。**
    原因：「只输出 JSON」的 cue 被追加成一条单独的 user 消息，历史里出现两条连续的 user——要求严格交替的本地模板拒绝【实现 2026-09-28】。
    对策：cue 接在最后一条 user 消息末尾（字符串空一行接上、分块追加一块）（06 §9.3）。
212. **每次重启应用，第一次结构化任务都先白撞一次已知的 400（本地模型上是几十秒的强制工具那一趟）。**
    原因：学到的上限只在进程内存里【实现 2026-09-28】。
    对策：持久化——读仍是同步内存，写穿到库，带时间、7 天过期；不进配置备份与同步（06 §9.4）。
    **改口留痕**：参考实现原定「会话级、不持久化」（理由：持久化等于替探测维做决定），2026-09-28 改判；过期与作废规则就是那条理由的答案。
213. **两个窗口各自学到不同的上限，重启后其中一个被抬了回去，又撞一次 400。**
    原因：库侧 upsert 按「后写赢」，窗口 B 的较高档盖掉了窗口 A 的较低档；或紧跟写入后的「忘掉」先落了库【实现 2026-09-28，变异测试钉住「只降」「过期可覆盖」】。
    对策：SQL 只在新值更弱、或旧行已过期时覆盖；写与删串成一条链（06 §9.4）。
214. **学到的上限永远不过期——或者反过来，一重启就被当成坏数据删掉。**
    原因：前者：学到的时间在未来（学到后时钟被拨回），「未满 7 天」一直成立；后者：未来余量设成 0，两个窗口用同一个时钟盖时间、落库却不分先后，差几毫秒就被当成拨回【实现 2026-09-28】。
    对策：学到的时间在未来一小时以上才不算数、载入时删；余量一小时（06 §9.4）。
215. **在模型面板里点了探测、端点也答了话，面板仍显示「这条线路拒绝结构化输出」。**
    原因：探测清掉了学到的上限，面板却只在打开时读了一次存储【实现 2026-09-28，review 中实际发生】。
    对策：存储提供订阅入口 / 版本号，界面读者订阅它；探测报告带「端点答没答话」，只有答上话才作废，取消的、一次都没答的不算（06 §9.4）。
216. **给学到的上限和探测出的上限用同一条过期规则：探测值满 7 天后，作者字段里的上下文上限悄悄变了。**
    原因：被动的值（400 教会的）不在作者的字段里，过期只是多撞一次 400；主动的值（作者点的探测）写进作者的字段，过期会让字段无声地变【实现 2026-09-28，设计取舍】。
    对策：学到的会过期、改声明或重新探测即作废；探测值不过期、重新探测时覆盖（06 §9.5、01 §1）。

## AC. 第三方 ④ 面的思考默认值与关闭结局、兼容层的非法值、中转站作者前缀（详见 03 §3.5、§4.1、02 §1 表后、06 §2、01 §9.2）

来源：simple-ai-writer PR #733（`docs/api/reasoning.md` §1.2 / §1.7 / §2.2、`docs/api/landscape.md` §7 第四、第六、第十四、第二十个样本，2026-09-28，
DeepSeek `/anthropic`、百炼 `/apps/anthropic`、智谱 `/api/anthropic`、MiniMax `/anthropic` 官方直连各一次；Google AI Studio 直连）、`docs/api/capability-resolution-lld.md` §9.8（2026-09-27，规范化 id）。

217. **④ 兼容层收下 `thinking:{type:"disabled"}`、200，模型照想、账单照付，请求侧没有任何信号。**
    原因：`disabled` 在第三方 ④ 面上有三种结局——收下真关（DeepSeek v4-pro / flash、百炼千问、智谱 4.6、MiniMax-M3）、拒绝会响（智谱 5.3 系 1210、百炼托管的 M2.5 / glm-5.3）、**收下但照想**（MiniMax M2.7、百炼上的 kimi-k2-thinking）；第三种 200 且没有任何警告字段【实测 2026-09-28，每格一次】。「省略 = 用默认」的默认也按平台 × 模型分：DeepSeek ④ 默认想、MiniMax-M3 ④ 默认不想。
    对策：思考类目的 `offSpelling` 按 (平台, 模型) 声明；「关没关」只看响应里有没有思考内容，不看请求发了什么（03 §3.5）。
218. **响应里有一个 `thinking` 块但文本是空的——读成「没想」，或读成「关不掉」，两种都错。**
    原因：Claude 当前代默认 `display:"omitted"` 文本空但签名有、想了且计费；百炼上的千问文本有、`signature` 恒为空串；百炼上的 kimi-k2.6 不发 `thinking` 与 `disabled` 时都回文本与签名都空的块，是真没想（显式 `enabled` 才有文本）【实测 2026-09-28】。
    对策：判「想没想」看文本或签名**至少一个非空**；空块要容忍、不当错误；空块不等于没想，也不等于关不掉（03 §4.1）。
219. **④ 客户端收到的 400 点名的是 `enable_thinking`——请求里根本没有这个字段，按 `thinking` 找原因找不到。**
    原因：百炼 ④ `/apps/anthropic` 是翻译层：`thinking` 被翻成自家 ① 方言 `enable_thinking` 下发，上游（MiniMax-M2.5、glm-5.3）拒绝时原文原样传回：`<400> InternalError.Algo.InvalidParameter: The value of the enable_thinking parameter is restricted to True.`【实测 2026-09-28】。
    对策：按文案做「按 400 学降级」时，正则匹配参数名不匹配本族字段名；翻译层的拒绝按「上游说了什么」读，字段名对不上就查 03 §3.5 的对照表（06 §2）。
220. **拿 `thinking.type:"bogus"` 探测「这台会不会校验」，MiniMax 上 200 了，而且思考被打开了。**
    原因：MiniMax ④ 什么都收（`top_k:99999`、`temperature:2.5`、顶层未知字段都 200），非法的 `thinking.type` 被当成「开」；同一值 DeepSeek 422 点名枚举、智谱回 1210、百炼 400 `Request body format invalid`——四家四种【实测 2026-09-28】。
    对策：非法值探测只在会响的家用；MiniMax 上不拿 `bogus` 探测，「按 400 学降级」在它身上什么都学不到；`top_p:1.5` 是它唯一撞出来的 400（03 §3.5）。
221. **模型名填错了（`MiniMax-M3.1-Flash-Preview`、DeepSeek ④ 上随便一个名字），200、有答案，账单也对得上——只是不是你以为的模型。**
    原因：MiniMax ④ 对目录里没有的模型名静默改映射，响应 `model` 是 `MiniMax-M3`【实测 2026-09-28】；DeepSeek ④ 文档明写 `claude-opus*` → v4-pro、其余与不认识的名字 → deepseek-flash，不报错 📄；百炼 ④ 则 400 点名 `does not exist`。
    对策：回显比对把响应 `model` ≠ 请求 `model` 记成一条告警（06 §4.1）；不把「200 有答案」当模型名正确的证据（06 §2）。
222. **Gemini 请求里 `thinkingLevel` 写成小写 `"low"`，审查时按参考页「全大写」判它写错了。**
    原因：AI Studio 直连运行时不分大小写，`"low"` 与 `"LOW"` 都 200、思考 token 同一范围；会 400 的是枚举外的值（`"lowest"` → `Invalid value at 'generation_config.thinking_config.thinking_level' …`）【实测 2026-09-28，gemini-3-flash-preview / 3.8-flash】。另：3.8-flash `low` 答一个词时 usage 不带 `thoughtsTokenCount`，不等于没想。
    对策：发小写不算错、不据此判错；照参考页发大写仍是稳妥写法；缺 `thoughtsTokenCount` 不当「没想」的判据（03 §2）。
223. **中转站上 `[x]gpt-5.6-sol`、`特价kiro | gpt-5.6-sol` 查不到目录里的严格 schema 名单与上限，自动档停在 `json_object`、规划上限用缺省——同一个模型在官方平台上却查得到。**
    原因：作者前缀让按 id 查目录的逻辑认不出；旧对策「不加剥前缀规则、让作者手动声明」（怕吞掉别家中继的别名）使目录事实在中转站上整体丢失【实现 2026-09-27，P6b】。
    对策：**规范化 id，只在中转平台上做**——渠道前缀表最长匹配优先、否则去开头 `[…]`、再去 `vendor/`；只用来查目录，平台格与上游格仍按原始 id 匹配，目录上限只进规划不进 `max_tokens`；「所有平台都去」已由金标收回（离线，非实测：官方平台上的 `[特价kiro量]claude-opus-5` 也开始提档）（01 §9.2）。
